# Architecture

Technical source of truth. Other docs link here instead of restating schemas or protocol details. For rationale behind these choices, see [decisions/](decisions/).

## System overview

```
React SPA ──REST (Hono RPC)──▶ Worker (Hono) ──▶ D1 (users, auth, board metadata)
    │                              │
    ├────WebSocket (per board)─────┼──▶ BoardDO (one per board)
    │                              │     ├─ WebSocket connections (hibernation)
    │                              │     └─ SQLite: columns, cards, ordering
    │                              │
    └────WebSocket (app-wide)──────┴──▶ PresenceDO (one global instance)
                                         ├─ WebSocket connections (hibernation)
                                         └─ SQLite: presence (last seen, timezone)
```

The SPA talks REST (Hono RPC) for auth and the board list, and opens one WebSocket per board for live state. The Worker routes `GET /boards/:id/ws` to the board's Durable Object via `idFromName(boardId)`. There is exactly one `BoardDO` per board; it owns all board state and all live connections to that board.

## Components

### Web (`apps/web`)

Vite + React SPA with TanStack Router + TanStack Query; drag-and-drop via dnd-kit.

TanStack Query owns server state:

- Board state (columns, cards, comments) arrives exclusively over the WS: the snapshot on connect populates the `['board', boardId]` cache (board content has no REST endpoint); REST covers auth, profile/account, board metadata (`GET /boards/by-key/:key`, `GET /boards`), and members.
- Authoritative base-state rebase & production `BoardReconciler`: `useBoardSocket` delegates mutation queuing, server message reconciliation, and optimistic rebase directly to `BoardReconciler` (`createBoardReconciler`), the single production transition implementation shared verbatim between socket runtime and regression suites (`apps/web/test/reconciliation.spec.ts`), eliminating test-model duplication. The reconciler maintains `baseState` as authoritative server state; accepted mutation broadcasts (both peer updates and own echoes) apply in server order directly to `baseState`. Own echoes retire their rollback timers and pending map entries. Remaining optimistic mutations in `pending` rebase in send order over `baseState` (`syncCache`), guaranteeing convergence and server-order last-write-wins (LWW) without skipping echoes.
  Coverage is two-layered: the deterministic-logic layer (`apps/web/test/reconciliation.spec.ts`, run service-free with no browser or local stack) drives the production reconciler primitives directly over fixed frame orderings, while the real-runtime layer (`apps/web/e2e/sync.spec.ts`) proves the same behavior through live services — two signed-in browser contexts on one board, a peer `column.rename` accepted by the live BoardDO between a client's optimistic rename and its own outbound frame, convergence of both clients and of a freshly opened third client's snapshot on the server-ordered last write, over a single uninterrupted socket (one snapshot, no reconnect).
- Optimistic rollback removes the rejected or timed-out mutation and rebases the remaining pending mutations over authoritative server state. No inverse callbacks are constructed or stored; peer changes and accepted lifecycle events remain authoritative.
- Drag-and-drop performs an optimistic cache update, sends the mutation over WS, and rolls back if the DO rejects or the echo never arrives (timeout). Card bodies own drag measurements; families remain stationary while a compact portaled preview and explicit boundary marker show the move. `card-drop.ts` orders direct same-status siblings or destination roots, normalizes descendant targets to displayed peer boundaries, and preserves one-row fractional moves. Pointer collision excludes clipped canvas regions; keyboard navigation follows logical peers/statuses and includes the tail slot (ADR 0058).
- Missing-column rejection: `card.create` and `card.move` validate that the destination column exists in DO SQLite storage; if the destination column was deleted concurrently, the DO rejects the mutation, triggering optimistic rollback rather than stranding active cards in non-existent columns. (Mutations targeting missing cards remain accepted silent no-ops).
- Upload insertion conflict behavior: `MarkdownEditor` tracks in-flight image uploads via dynamic anchors (`computeEditRange`, `adjustAnchorOffset`). User typing during an active upload adjusts anchor boundaries. If the user edits text within a selected range while an upload is pending, `rangeEdited` triggers conservative insertion at `boundedEnd` rather than replacing text, preserving all user edits and deterministically positioning the caret.
- Strict SVG clipboard conversion: SVG clipboard paste is opt-in for card descriptions only (`allowSvgPaste` on `MarkdownEditor`, passed by `DescriptionEditor`); comment/reply editors, the toolbar Image picker, general attachment uploads, and server download-only isolation (`Content-Disposition: attachment`) remain unchanged. Clipboard payloads are selected in priority order (SVG file with MIME `image/svg+xml` or empty-MIME `.svg`, SVG MIME string, whole `text/plain` SVG document, then supported raster files; prose containing SVG or fenced code remains native text). Conversion runs client-side via `compressImage(..., { rasterizeSvg: true })` producing a single WebP attachment (quality 0.8, max edge 2048, no upscaling), rejecting DOCTYPE/entity declarations, parsing in a detached XML DOM, validating SVG root and SVG namespace (re-parsing with standard SVG namespace if omitted so children inherit identity), calculating dimensions/viewBox (synthesizing a viewBox when downscaling unviewboxed SVGs to prevent clipping), enforcing root CSS dimension caps with `!important`, decoding through `HTMLImageElement` with an object URL and 10s timeout, and blocking script/external network execution. Conversion strictly requires `image/webp` output and never falls back to original SVG, PNG, or vector bytes on error.
- Retained description editor & pending upload lifecycle: `DescriptionEditor` mounts `MarkdownEditor` once on first edit and retains the instance across Preview/Edit toggles until card disposal (`active` prop inerts toolbar, textarea, and trailing controls without unmounting in-flight state). `CardModal` acquires `descriptionUploadingRef` synchronously before starting async conversion, guarding Save and Ctrl/Cmd+Enter and exposing inline accessible status (`role="status"` "Converting and uploading image…") and busy notices (`role="alert"`) that survive into preview mode. Preview/Escape functions as preview rather than cancellation; completion while previewing updates rendered text without stealing focus to hidden controls; and card disposal invalidates pending operations via a liveness ref to prevent late draft/focus mutations without deleting already-published attachments. Upload caret restoration waits for the exact controlled value in a layout effect: an animation frame can run before the new value commits and clamp the selection against the old text. The one-shot pending selection is cancelled by native/toolbar edits or inactive/read-only state, applies only to the same connected textarea and never changes focus.
- Stable Markdown renderer identity across viewer navigation: the `react-markdown` `components` maps (`standardMarkdownComponents`, `youtubeMarkdownComponents` in `MarkdownEditor.tsx`) are module-level constants rather than per-render object literals, and the embedded-image renderer (`StableMarkdownImage`) reads its preview index and open callback from `MarkdownPreviewContext` instead of props. Because the component types are referentially stable, opening or closing the URL-backed attachment viewer (`?attachment=<id>`) re-renders the rendered description or comment without remounting its subtree, so the embedded image button that invoked the viewer keeps its DOM identity and remains a valid focus-return target.
- Acceptance-aware authored settlement & locked-editor lifecycle: `ws.send` is an unconfirmed network transmission, not operation completion; the server echo or snapshot is authoritative. Authored operations (`card.update` from Save, `comment.create`, `comment.update`, `comment.delete`) register with `notifyMutation` in `useBoardSocket`. The mutation status lifecycle spans `accepted`, `rejected`, `timeout`, `uncertain`, and `verified-retry`. While an authored operation is pending or uncertain, its specific editor lane locks read-only (`readOnly` and disabled controls), displaying submitted text byte-for-byte to prevent divergent drafts, while unrelated composer lanes remain editable. On live-socket timeout of an authored operation (`mutationSubscribersRef.has(mutationId)`), `useBoardSocket` rolls back the local optimistic mutation and initiates an authored-only resync by closing the transport (`ws.close(4000, "authored operation timeout resync")`); ordinary instant mutations or attachment deletions do NOT close the transport. Upon receiving a snapshot, the reconciler applies the snapshot, and the TanStack Query cache is updated (`queryClient.setQueryData`) *before* notifying mutation subscribers. If the snapshot contains the mutation, it settles as `accepted` without entity duplication; if verified absent, it settles as `verified-retry`, unlocking the editor with the exact raw draft for explicit user retry or discard. Raw editor text is distinct from normalized wire body. Reconnects and disconnects mark pending authored operations `uncertain`, disabling retries until snapshot verification. There is no automatic resend, no offline queue, and no toast notification.
- Acceptance-aware checklist text: checklist creation and inline text edits use the existing mutation settlement subscriptions. Shared title validation runs before transmission, and exact raw drafts survive rejection, dropped sends and verified absence. Pending or uncertain submissions lock only their own lane and remain mounted until authoritative acceptance or snapshot verification. Unsent checklist text participates in the modal close guard; peer-deleted edits offer explicit save-as-new or discard recovery. Checkbox toggles and deletion remain instant mutations (ADR 0062).
- Acceptance-aware creation dialogs: `BoardView` allocates one entity id and mutation id per attempt and calls `subscribeMutation` before `sendMutation` for `card.create` and `column.create`. Only `accepted` closes the dialog, whether delivered by the server echo or authoritative snapshot verification; the optimistic cache is never acceptance evidence. `isMutationPresentInBoardState` checks a column by id and a card by id in active **or archived** cards, so later peer edits or archival do not trigger duplicate creation. A false send retires tracking and leaves the draft editable with "Not connected — changes won't send."; a rejection retires tracking and retains the draft with the server error. `timeout` and `uncertain` keep fields, submit and dismissal locked with "Checking whether creation completed…", using the existing socket resynchronization path. An authoritative snapshot that verifies absence emits `verified-retry`, retires the attempt and unlocks the retained draft with "Creation was not confirmed. You can try again." for explicit retry, never automatic resend. Terminal connection failure exposes a connection **Retry** outside the disabled form fieldset, still usable while creation is pending. Terminal attempts and unmount unsubscribe and retire tracking.
- Reconnect logic & loaded board page durability: exponential backoff; on reconnect, request a fresh snapshot — never try to replay missed events. Discard pending timers on reconnect; no localStorage for board data — the server is the source of truth. Once an initial snapshot has loaded, terminal connection failure (circuit breaker tripped after 3 unsynchronized failures) preserves the mounted board page, open card modals, and in-progress drafts in memory, exposing an actionable `Retry` callback in the board header and modal footer that resets the attempt budget, rather than unmounting the board page. Only an initial connection failure prior to any snapshot displays the full-page failure screen.
- Development info reads nothing on a timer ([ADR 0064](decisions/0064-instance-github-app-webhook-development-info.md)). Card fronts show a compact pull request badge from one board-wide read, `GET /boards/:id/development` (`boardDevelopmentQueryOptions`): the badge names the pull request still in play (open, then draft, then merged, then closed; the most recently updated within a state) and a count when there are several. The card's Development section reads `GET /boards/:id/cards/:cardId/development` (`cardDevelopmentQueryOptions`) and offers a repository picker fed by `GET /boards/:id/connected-repos`, Create branch and Create pull request in the picked repo, a manual link by number or URL, and an unlink button on each pull request and each branch. A card-scope `github.invalidated` hint on the board socket, and a reconnect snapshot, mark `card-development` and `board-development` stale (`invalidateDevelopmentQueries`) and the next read installs the truth; there is no interval, no focus or visibility refresh and no per-viewer GitHub call. Both queries are board-private cache keys, removed on a confirmed access denial like the rest. A card's link draft (`usePullRequestLink`) lives in the card modal so the modal's dirty guard and Escape ladder see it; linking the same pull request twice changes nothing, so a failed attempt is simply submitted again. The old Commits tab is gone: development info keeps only each branch's latest commit.
- Deferred focus restoration yields to a live keyboard owner, and resolves its target at frame time: `restoreFocusSoon` (`apps/web/src/lib/focus.ts`) is the single helper for focus that must return to a trigger after an overlay closes or an inline editor commits. It accepts either an element or a resolver, and a resolver runs **inside** the single animation frame — so a card whose node was replaced or re-parented while the modal was closing (a peer move putting it in another column) still regains focus, because the lookup happens after the move rather than before the frame. The one-frame delay and the `isConnected`/`inert` guards are kept, and the restore proceeds only while focus has fallen back to the document: if anything else has taken the keyboard in the meantime (a user or test keystroke landing in another field), the restore is abandoned instead of stealing focus. Callers are the column rename commit/cancel path (`ColumnView`) and the overlay-close restores in `BoardView` (card modal, column delete alert, archived cards, member drawer, mobile filter sheet); `closeCard` is the site that passes a resolver, the rest pass the captured element. Board-level shortcuts depend on this contract: an unconditional restore frame can land between a field's focus and the next keystroke, so `n`/`c`/`m`/`/` no longer see an input target and the keystroke is consumed as a shortcut instead. The same unconditional pattern still exists in other overlays (`BoardListPage`, `BoardAddMemberDialog`, `CardArchiveDialog`, `MarkdownEditor`, `CardModal`); those sites are not on the repaired paths and remain a known follow-up.
Routes: `/` (Home, see below; never redirects), `/profile` (account settings: display name, sign-in email, password, avatar upload, GitHub link), `/mcp-server` (session-authenticated MCP credential management), `/account-invites` (admin-only signup invite management), `/account-github` (admin-only instance GitHub App setup), `/all-workspaces` (admin-only: every workspace in the instance, each linking to `/w/<id>`; non-Admins are redirected to `/`), `/w/<id>` (one workspace's boards), its `/w/<id>/members` page (workspace members only) and `/w/<id>/settings` page (workspace owner or admin only; others are redirected to `/w/<id>`), `/join-workspace/<id>` (accepts a workspace invitation), `/login`, `/signup`, `/board/:boardKey`. Every signed-in page renders inside the app shell (the sidebar and header: navigation links, avatar/email, sign out); everything but the auth pages sits behind the root route's session check. The public board route resolves the human board key to metadata via `GET /boards/by-key/:key`, mounting `BoardView` with the internal UUID.

Home (`/`, `HomePage`, [ADR 0066](decisions/0066-workspace-model.md)): built on the client from the two existing lists, `GET /workspaces` and `GET /boards` (no dedicated endpoint). It renders one group per workspace the viewer is a member of (`access: "member"`), each titled with a link to `/w/<id>` and with its own "New board" button, whose dialog creates the board in that group's workspace (`POST /boards` always names `workspaceId`). Boards in a workspace the viewer is not a member of (`access: "guest"`, which `GET /boards` returns with `workspaceName`) sit together under one "Guest" heading, each row naming its workspace, with no New board button. Both lists carry only what the viewer holds as a member or Guest, an instance Admin included, so an Admin's Home has no other person's workspace or board (those are on `/all-workspaces`). With no member workspace and no guest board, Home shows "No workspaces yet."; the heading's "Create workspace" button is always there. Home keeps no remembered workspace: the old `foxban-last-workspace` redirect and the resolver's `personal_<userId>` fallback are gone, so `/` is the same on every device. Board rows are the shared `BoardRow` (name, key, Workspace/Restricted label); the per-board actions menu stays on a workspace's own board list.

- Same-column subtask families render inside their parent card, from one derived hierarchy: `BoardView` memoizes `buildSubtaskHierarchy` and owns session-only collapsed-family state (a family nobody closed is open, deleted ids are pruned, nothing is persisted or sent). `columnCards(state, columnId)` returns every card stored in a column — archive counts, the PR query set and column counters need that flat answer — while `columnRootCards` returns the draggable/rendered roots (a child nests only under a parent in the same column) the board and drag ordering use. A filter keeps a match reachable by rendering its active ancestor path and auto-expanding it at render time only (`renderedCollapsed`), so clearing a filter restores the reader's own expansion; a context ancestor is shown but not counted as a match. The sortable `<li>` is structural: a focusable body region owns dnd-kit's attributes, listeners and click-to-open, and the family footer/rows are siblings inside the same visual card, so a child control can never lift or open the parent. The drag preview retains the task body and progress footer, collapses family rows, and bounds its height, and `closeCard` resolves focus at frame time — the card's own control, then the nearest visible ancestor's disclosure or body, then the Search cards input.

### API Worker (`apps/api`)

Hono on Cloudflare Workers. Exports the app type for the RPC client — `export type AppType = typeof app` — consumed by `hc` in `apps/web`; keep this export stable.

Auth: session cookie, sessions in D1. Configured account administrators (`ADMIN_EMAILS`) act as global board operators for direct access: `requireMember` queries `boards` directly by id without creating `board_members` rows, bypassing membership for all guarded board, attachment, and WebSocket routes. Listing is not operator-wide: by default `GET /workspaces` and `GET /boards` return only what the viewer has as a member or a Guest (board owner or `board_members` row), an Admin included, and an Admin's guest workspace is tagged `access: "guest"`, never `"operator"`. An Admin gets every workspace only from `GET /workspaces/all` (`requireAdmin`: 403 for anyone else, 401 without a session; rows are tagged `member` or `operator` and count every board), and `GET /boards?workspaceId=<id>` lists every board of that workspace when the Admin is not a member of it (the Operator's workspace page); inside a workspace they belong to, they list as a member does. Ordinary users remain membership-scoped, and `requireMember` enforces the join (missing boards and unauthorized access both return 403). The app shell marks Operator access (an Admin who opens a workspace or board only through instance-Admin power: outside the workspace, or a member of it opening a Private board they were not added to) and Guest access next to the workspace name in the breadcrumb. `GET /boards/:id/members` returns only actual board members. Board metadata editing via `PATCH /boards/:id` (display name, unique uppercase key, validated icon and color) and permanent board deletion via `DELETE /boards/:id` are restricted to the board owner or configured account administrators; editing executes one atomic D1 UPDATE, maps unique board-key collisions narrowly to 409, and leaves BoardDO card storage and task numbers untouched.

Account routes: `GET /me` (which also says whether the account has a password: `hasPassword`) and `PATCH /me` (display name, GitHub disconnect); `POST /auth/email` and `POST /auth/password` verify the current password first, behind the same per-IP rate limit as login/signup. An email change is refused when it would alter configured-admin status; a password change rotates the PBKDF2 hash compare-and-set and atomically deletes every other session row for the user. Login session insertion requires the verified password hash to remain current, so a login paused across rotation cannot create a new session from the old password. Linking GitHub uses the instance GitHub App's user sign-in (`GET /auth/github/start`, state cookie, then `GET /auth/github/callback`, which exchanges the code with the App's client id and secret from D1, ADR 0064) and stores the login name plus GitHub's numeric user id (`users.github_user_id`, unique, so one GitHub account links to one foxban account). The callback redirects to `/profile`, `/profile?github=error`, or `/profile?github=taken` when another account already has that GitHub account; `PATCH /me` with `githubLogin: null` disconnects and clears both columns.

Log in with GitHub ([ADR 0065](decisions/0065-log-in-with-github.md)): `GET /auth/github/login/start` (public, `rateLimitAuth`) redirects to GitHub with the instance App's client id and a state kept in its own `github_login_state` cookie, and `GET /auth/github/login/callback` (public, `rateLimitAuth`) checks that state, exchanges the code with the same `fetchGitHubUser`, and looks the user up by `users.github_user_id` only, never by login name. A known id gets a normal session (`startSession`, so `POST /auth/password` revokes it like any other) and its stored `github_login` follows a GitHub rename; the redirect goes to `/`. Every other outcome redirects to `/login?github=error|cancelled|unlinked|exists|unavailable` (failed exchange or bad state, the person pressed Cancel on GitHub, no foxban account has that GitHub id and no invite let it sign up, a verified GitHub email already belongs to a foxban account, no GitHub App yet) and starts no session; the login page turns the reason into a message.

Sign up with GitHub (same ADR): the signup page's "Sign up with GitHub" link (shown only with an invite) is `/auth/github/login/start?invite=<token>`, which keeps the token in a `github_login_invite` cookie next to the state; the callback reads and clears it. A pending workspace invitation (the `#workspaceInvite=<workspaceId>.<token>` the login or signup page holds, which a full-page round trip would lose) rides the same way: the page's GitHub link adds `workspaceInvite=<workspaceId>.<token>` to the start URL, which keeps it in a short-lived httpOnly `github_login_workspace_invite` cookie only if it matches `^[\w-]{1,64}\.[\w-]{1,128}$`; the callback reads and clears the cookie, validates it again, and after a successful sign-in or sign-up redirects to `/join-workspace/<workspaceId>#invite=<token>` instead of `/`. A failed round trip goes back to `/login?github=...#workspaceInvite=...`, so a retry keeps it. A GitHub id no account has goes through `signUpWithGitHub`: it lists the GitHub account's verified emails (`GET /user/emails` with the user's token, which needs the App permission "Email addresses: read"; the token is not stored) and, if any equals an existing `users.email`, redirects to `?github=exists` ("sign in with your password, then link GitHub in Profile"), never linking by email. Otherwise it needs an invite: a missing, unknown or spent token is `?github=unlinked`, the same for all, and a valid one is spent in the same single D1 batch that inserts the user as email signup does (`createUserWithInvite`). The account keeps the primary verified email, or GitHub's `id+login@users.noreply.github.com` address when that email is on `ADMIN_EMAILS` or there is none, so GitHub signup never produces an Admin (Admin is derived from the email); if that no-reply address is on the admin list too (a `*@users.noreply.github.com` entry), the signup is refused with `?github=error` and nothing is created or spent. `users.password_hash` is the marker `*` (`NO_PASSWORD_HASH`), which matches no password, so password login answers the normal generic 401. An account created this way can only sign in with GitHub until it sets a password: `POST /auth/password` without `currentPassword` does that, only while the marker is there, with the same compare-and-set and other-session revocation as a change (a second call needs the current password). Until then `PATCH /me` with `githubLogin: null` and `POST /auth/email` are refused with 403 `PASSWORD_REQUIRED` (the email refusal precedes any duplicate or admin check), so the account can never lock itself out; Profile shows "Set a password" for it.

Workspace roles (ADR 0066): a workspace has admins and members, and no owner. `workspace_members.role` is `admin` or `member`; `workspaces.owner_id` is only the creator, kept as a column and read for nothing. Admins manage settings, invites, members and every board in the workspace, Private ones included; any member may remove themselves, which is how a member leaves. A workspace always keeps at least one admin: demoting or removing the last one is refused with `409 last_admin` ("Promote another member to admin first."), checked by the route, again by the access-change evaluation and commit, and finally by the `workspace_keeps_an_admin_*` triggers from migration 0022, which raise inside the statement so two admins demoting each other at once leave one. Role changes, removals and leaving all run as `workspace-member-role` and `workspace-member-remove` access changes, so every board of the workspace has its cached access fenced and its open sockets dropped, Private boards included (their admins are what a role change moves). An invitation is only as good as the admin who issued it: it lists, inspects and accepts only while its `invited_by` is still an admin of the workspace, so demoting or removing an admin retires the invites they issued (promoting them again makes those work until they expire). Without this a demoted admin could leave and accept the admin invite they kept. The accept checks it in the route's read, again where the `workspace-invite-accept` attempt reserves the workspace (`authorityAssertions`), and again in `evaluateCommit` and in the commit's membership insert (`INVITER_IS_ADMIN`). A refusal answers `400 workspace_invite_unavailable`, the same as an expired or revoked invite and without saying why; a demotion that lands between the route's read and the reservation answers `409 access_change_conflict`, and a retry then gets the 400. Migration 0022 turned owner rows into admin rows. SQLite cannot alter the `role` CHECK, so `owner` is still an allowed value there, but a trigger rewrites any `owner` insert (the previous Worker's workspace creation) to `admin` in the same statement and nothing reads it; a later migration can drop the value once no such Worker can run.

Who may open a board (ADR 0066): an Operator, the board's owner, a board member (any `board_members` row, so a Guest too), a member of its workspace while it is a Workspace board (`access_mode='workspace'`), or an admin of its workspace whatever its mode. A Private board (`access_mode='restricted'`) is therefore closed to a workspace member who was not added, and open to the workspace's admins, who also manage it (rename, move, delete, members, columns) with no `board_members` row. The rule has one copy in `apps/api/src/auth.ts`: `boardOpenSql` / `boardManageSql` build it as SQL (board alias, viewer expression, and an operator term each site chooses: default lists leave it out, `GET /boards?workspaceId=` counts an Admin outside the workspace, `transfer-options` never has it), and `canOpenBoard` / `canManageBoard` decide it in TS from already-read rows (`toBoardRow`, the BoardDO's `currentBoardAccess`, and `evaluateCommit` in `access-changes.ts`). Every surface uses them: `findAccessibleBoardWhere` (behind `requireMember` and `GET /boards/by-key/:key`, so REST routes and the WebSocket connect), the `GET /boards` list, the BoardDO re-check, the member and candidate reads, the `PATCH /boards/:id` write predicate, `transfer-options`, the workspace board counts, the MCP `get_board` member read, and the recipient visibility and board predicates in `access-changes.ts`. A new surface uses the builder and adds a row in `apps/api/test/workspace-admin-private-boards.test.ts`. Assignee eligibility (`currentAssigneeEligible`, MCP's `effectiveBoardMemberClause`) is deliberately unchanged: it follows board members and Workspace-board members, so an admin who wants to be assigned work on a Private board is added to it. Board metadata carries `viaWorkspaceAdmin`, true for an admin who opens a Private board only through the workspace (not its owner, not a board member); the board page shows a note for it and it grants nothing.

Deleting a workspace (ADR 0066): `DELETE /workspaces/:id` is for a workspace admin only. A member, a Guest, a stranger and an Operator who is not a member of it get `403` (an instance Admin who is also an admin of the workspace deletes it like anyone). It is one D1 batch, so one transaction: it reads the member ids, then runs a single `DELETE FROM workspaces` that carries the caller's admin row, "no row in `boards` for this workspace" (every board, including a Private one the admin cannot open) and "no `access_change_scopes` row for it", and only then deletes the workspace's members and invites, each guarded by the workspace row being gone (so a refusal leaves them alone and the last-admin triggers, which stand down once the row is gone, never see the member delete). A refusal is `409 workspace_not_empty` ("Move or delete this workspace's boards first.") or `409 access_change_conflict` (a journaled access change holds the workspace, which includes a board move into or out of it). Because the emptiness check and the delete are one statement, a board created or moved in at the same moment either lands first and is seen, or finds no workspace: `POST /boards` inserts only while the creator's membership row exists, a board move reserves its destination's scope and asserts the mover's membership there, and the `boards_workspace_valid_insert` and `boards_workspace_required_update` triggers from migration 0012 refuse any board placed in a workspace that does not exist. No migration is needed. Former members with an open presence socket get a `workspace.invalidated` hint, best effort; anyone else sees the workspace go when their lists next refresh.

Board membership routes are guarded by `requireMember`. Candidate discovery returns registered users not already represented in `board_members`; additions and removals use stable user ids. `DELETE /boards/:id/members/:userId` is idempotent for absent rows but rejects the board owner and the caller themselves. Deleting a membership row revokes subsequent guarded REST requests and WebSocket handshakes; it does not actively evict a socket that already passed the connect-time check.

Column structure is a separate owner/admin boundary: only the owner of that particular board or an existing account administrator may create, rename, reorder or delete its columns. Owning another board grants no column rights here. Ordinary members retain card collaboration, membership management and label operations; board creation and the existing owner/admin rules for board metadata and deletion are unchanged. See [ADR 0050](decisions/0050-owner-admin-column-management.md).

Cross-board card transfer routes: `GET /boards/:id/transfer-options` returns accessible destination boards with live columns, by the member, Guest and workspace-admin rule for everyone: an instance Admin may open the source as an Operator but is not offered every board in the instance. `POST /boards/:id/cards/:cardId/transfer` executes an idempotent saga:
- Source preparation: validates that the card has no cross-card relations/links (rejecting with HTTP 409 if present), records operation in `card_transfer_operations` (state `'prepared'`, monotonically increasing generation per card), creates a non-expiring write fence in `card_transfer_locks`, and exports the bundle. Reusing an already terminated (finalized or aborted) `transferId` is rejected with HTTP 409 Conflict. The source write fence remains active until terminal state (`finalized` or `aborted`) is reached; it does not expire via TTL.
- Markdown URL rewriting: card descriptions and comments have their attachment URLs rewritten from `/boards/:sourceBoardId/attachments/:id` to `/boards/:destinationBoardId/attachments/:id` via `rewriteAttachmentUrls` in `@foxban/shared`, using exact AST parser token offsets (`resourceDestinationString`, `definitionDestinationString`) to preserve code spans, brackets, entity encodings, and angle brackets.
- R2 copy & staging leases: attachment files are copied to transfer-scoped destination R2 paths (`${destinationBoardId}/${transferId}/${attachmentId}`), with destination staging leases registered in `attachment_cleanup`.
- Destination import: destination BoardDO checks for an existing receipt. If an abort tombstone exists (`taskNumber = -1`), import is rejected with 409. It performs pre-write lease validation inside the transaction, verifying active staging leases in `attachment_cleanup` (`delete_after > now AND claim_token IS NULL AND deleted_at IS NULL`) for all bundle attachments before executing any database writes or allocating destination task numbers; expired, claimed, or tombstoned staging leases throw `ImportConflictError(409)` triggering transactional rollback without partial commits. Transfer U import consumes only U's staging row (`destObjectKey`), while aborted transfer T's staging rows remain untouched in `attachment_cleanup` until collectible. On success, allocates a monotonic destination task number and fractional position, and persists receipt in `card_transfer_receipts` (keyed by `transfer_id`).
- Two-phase finalization & terminal destination fencing: source deletion occurs only after destination commit. In compensation handlers and lock release, destination abort (`CARD_TRANSFER_ABORT_PATH`) is established first. If destination committed, source finalizes the exact current generation (cascading card aggregate and marking operation `'finalized'`); if destination aborted, destination records an abort tombstone (`taskNumber = -1`), source releases the lock, and operation marks `'aborted'`. If destination is unreachable, the source write fence is retained. Worker compensation performs no foreground R2 deletion; uncommitted transfer-scoped staging blobs are safely collected by the destination BoardDO TTL durable collector / alarm sweep, where successful deletion stamps a permanent tombstone (`deleted_at`).
- Frontend transfer operation ID semantics: `TransferCardDialog` manages the client-side `transferId`. When submitting a transfer, the operation ID is preserved across ambiguous network failures or 500 server errors so retries remain idempotent and resume the in-flight saga. A terminal conflict instead rotates the dialog to a fresh UUID (`transferId`) and clears the destination binding, because the supplied operation can never commit. Terminality is decided by `isTerminalTransferConflict(status, data)` in this order:
  - `code === TRANSFER_TERMINAL_CODE` (`"transfer_terminal"`, exported from `@foxban/shared`) — the stable primary discriminator. Every terminal transfer rejection the Worker and BoardDO emit (terminated/reused operation id, card or destination identity mismatch, generation mismatch, abort tombstone, lock mismatch, destination identity unknown) carries this code alongside its HTTP status, and the Worker forwards the code when relaying a DO 409, so prose is never load-bearing.
  - HTTP 410, or `aborted: true` in the body.
  - An uncoded 409 is non-terminal regardless of its prose — the operation is still live server-side — so the dialog preserves the operation id and shows no new-operation notice. Human error text is display-only.

  Changing the destination board or column also rotates the id, so a resubmission never collides with a receipt or generation lock bound to the previous destination.

Instance GitHub App ([ADR 0064](decisions/0064-instance-github-app-webhook-development-info.md)): an Admin creates the instance's one GitHub App through GitHub's app-manifest flow. `GET /github-app` (status: the App's public fields and an install link, plus `canCreate`) and `POST /github-app/manifest` (the manifest, built from `appOrigin`, and the GitHub form target carrying a CSRF `state` cookie) are Admin-only; `GET /auth/github-app/manifest/callback` checks the state cookie, converts GitHub's `code` (`POST /app-manifests/{code}/conversions`) and writes the single `github_app` row, then redirects to `/account-github?githubApp=created|error`. The private key, webhook secret and client secret are AES-GCM sealed (WebCrypto, column name as AAD) with the `GITHUB_APP_ENCRYPTION_KEY` Worker secret, which `scripts/deploy.mjs` generates only when the Worker has none; no response ever carries them, and the existing App is never replaced. The webhook URL in the manifest is `/webhooks/github`. This is the only GitHub App foxban uses: the per-board repository connection of ADR 0041 (the `boards.github_*` columns, `github_connection_states`, the connect, setup and callback routes and the env-configured App) was removed by migration 0020, so an upgraded instance starts with no App until an Admin presses the button.

Webhooks and connected repos (ADR 0064): `POST /webhooks/github` is public and authenticated by signature alone. It reads the raw body, checks `X-Hub-Signature-256` (HMAC-SHA256 with the decrypted webhook secret, constant-time) and only then parses; no App is 404, a bad or missing signature 401, an unparsable signed body 400. Every other outcome is 2xx, because GitHub does not retry failed deliveries; the only 5xx is a GitHub error while confirming an installation's owner (502), which GitHub shows in its delivery log. The App is public, so anyone can install it: `installation` and `installation_repositories` events add repos to `github_repos` (repo id, installation id, `full_name`, private flag) only when `installation.account.login` equals the App owner's login from `GET /app` (App JWT, case-insensitive); removals (`installation` deleted/suspend, `repositories_removed`) need no check, since only owned installations were ever connected. `pull_request`, `push`, `create` and `delete` events return `dropped` unless `repository.id` is a connected repo. A connected repo's `pull_request`, `push`, `create` and `delete` events become development info (below), `applied` when a card changed and `dropped` otherwise. `GET /github-app` (the Admin page) first re-reads the owner's active installations (`GET /app/installations`, an installation token, `GET /installation/repositories`, all pages) and makes `github_repos` match, so missed events heal; if GitHub cannot be asked it returns the last known repos with `reposRefreshed: false`. It also returns the App `owner`, the `ignoredAccounts` whose installs it skipped, and `settingsUrl` (the App's Advanced settings, where ownership is transferred), so the page can say why an install on another account connects nothing. `DELETE /github-app` (Admin) forgets the App so another can be created: it drops the `github_app` row, `github_repos` and the backfill queue in one batch, and keeps card development info and the PR and branch routes, whose ids are GitHub's and still match a new App on the same repos. GitHub keeps the App until its owner deletes it there. The private key GitHub returns is PKCS#1 and is wrapped into PKCS#8 in `github.ts` before WebCrypto signs the App JWT.

Development info from pull requests (ADR 0064): `github-development.ts` turns a connected repo's `pull_request` event into a write to each board that holds it. `task-keys.ts` reads task keys from the head branch, title and body: a board key (2 to 10 letters or digits, starting with a letter), a hyphen and a task number with no leading zero, not touching other letters or digits, case-insensitive, at most 20 distinct keys per event. `kr-42-fix` and `fix/KR-42_x` name KR-42; `KR-420`, `KR-42x` and `XKR-42` do not. Keys resolve to boards through `boards.board_key` (unknown keys fall away); boards also come from the D1 routing table `github_pr_routes(repo_id, pr_number, board_id)`, so a linked PR keeps updating after its text stops naming the key. The routing table is pointers only, no card data; the BoardDO writes it through `github-pr-routes.ts` (`syncPullRequestRoute`) after each webhook write, on a transfer and when cards are deleted, and reads join `boards` so a deleted board's pointer is ignored. Links follow the card: a board-key edit, archive and restore, or a title that stops naming the key leave them in place (existing links update whatever the text says), a transfer carries them in the bundle (`developmentPullRequests`) and points the routing table at the destination board before the import commits, and a purge deletes the rows and drops the board's pointer unless another card on the board still holds the PR. A pointer is a hint that heals itself: a stale one is dropped by the next event for its PR, so only the add before a transfer commits is awaited, and the drops run after the card is gone. Each board receives `POST /internal/github/pull-request` with the PR (`repositoryId`, `repository`, `number`, `title`, `state` of open, draft, merged or closed, `url`, `updatedAt`) and the task numbers its text named for that board's key; it links those active cards on first sight and updates every card that already links the PR. A row is written unless the stored `updated_at` (epoch ms, GitHub's own second-resolution clock) is later than the event's. An equal one still writes, because a follow-up in the same second as the stored event must win, while a write that would change nothing is skipped and not announced; so late deliveries cannot roll state back and a replay is idempotent and silent. Members read `GET /boards/:id/cards/:cardId/development` (`{ pullRequests, branches }`, newest update or commit first, no GitHub call; 404 for a missing or archived card). `push`, `create` and `delete` payloads carry no usable "last updated" field (`create` and `delete` have none; `push` has only committer-supplied commit timestamps), which is why branch events re-read the branch instead of trusting payload order.

Development info from branches (ADR 0064): `github-branches.ts` handles `push` (a `refs/heads/` ref; tags are ignored), `create` and `delete` (`ref_type: "branch"`). The branch name is read for task keys like a PR's text; a name that holds no key of a known board costs no GitHub call. Otherwise the Worker mints an installation token for the repo's installation (`github_repos.installation_id`) and re-reads the branch (`GET /repos/{repo}/branches/{name}`): the tip's sha, first message line, committer time and the branch's web URL, or a 404. Whatever the event said, the card shows that answer, so a `delete` for a branch that exists again changes nothing and a `push` for a branch that is gone removes it. A branch's boards come from the keys in its name and from the D1 routing table `github_branch_routes(repo_id, branch_name, board_id)` (migration 0021; pointers only, no card data), so a linked branch keeps updating, and a `delete` still applies, after its board's key is edited or its card moved to another board. A routed board with no key match is told with no task numbers, so it updates only cards that already link the branch. The BoardDO keeps the table current through `github-branch-routes.ts` (`syncBranchRoute`), like the PR table: after each branch write and unlink, before a transfer import commits (and again after it), and when cards are purged or leave in a transfer; reads join `boards`, so a deleted board's pointer is ignored. Branch links follow the card like PR links: the transfer bundle carries the branch rows (`developmentBranches`, each with its `observedAt`, so the read that ordered a row still orders it) next to `developmentPullRequests`. Members unlink a branch with `DELETE /boards/:id/cards/:cardId/development/branches/:repositoryId/:name` (the name URL-encoded, since it may hold slashes): it removes the row, records a `branch` tombstone in `card_development_unlinks` so key matching never links that branch to that card again, updates the pointer, announces the card and answers with the card's development info (404 `not_linked` when the card did not link it). A branch cannot be linked by hand. Each board receives `POST /internal/github/branch` with `{repositoryId, repository, name, head | null, observedAt, taskNumbers}`; `observedAt` is when the re-read began and orders writes (a write is skipped when the stored row came from a later read), and cards are announced only when the shown commit changed. Branch rows keep one latest commit, never history. A removal by a delete event leaves no marker, so a read that began before a delete but is applied after it can briefly bring a branch back; the next event for that name corrects it. The GitHub calls (an installation token and one read) run inside the webhook request, well inside the 10 seconds GitHub allows.

Backfill on connect (ADR 0064): `github-backfill.ts` fills cards with a repo's existing work when it is connected. A repo added by an owned `installation` or `installation_repositories` event is queued in D1 `github_backfill_queue(repo_id, queued_at, run_after, attempts)`; the webhook then runs `drainBackfill` in `ctx.waitUntil` (after the 2xx, so the 10-second delivery limit does not bind) and the every-minute cron drains whatever is due, so the job is queue-less and survives any single invocation. The Admin page's re-read (`refreshConnectedRepos`) queues the repos it newly connects the same way, for a repo whose `installation` webhook never arrived; the cron drains them. A drain claims one due repo at a time under a lease (`run_after` pushed 2 minutes out) and stops claiming after 20 s or about 300 subrequests, well inside the 1000-subrequest limit. Per repo it lists open PRs (all pages, no window), closed PRs (`state=closed&sort=updated&direction=desc`, GitHub has no `since`, so it stops at the first PR whose `updated_at` is older than 30 days and keeps only those whose `closed_at` is inside the window) and all branch names (100 per page), then sends only PRs and branches that name a task key through `handlePullRequestEvent` and `writeBranch`, the same matcher and board writes webhooks use (a branch costs one `GET /branches/{name}`; the other branches cost none). Writes are idempotent (newer `updated_at` and later `observedAt` win, unchanged rows are not announced), so a rerun, a retry after a partial run, or a re-add changes nothing. A rate-limited call (429, or 403 with `Retry-After` or no quota left) holds the repo until `Retry-After` has passed and ends the drain; any other failure retries after 5 minutes times the attempt count and is dropped after 5 attempts. Limits: at most 10 pages per list and 100 key-naming PRs and 100 key-naming branches per repo (the oldest fall off; a resumable cursor would lift this), and it assumes the Workers Paid subrequest limit.

Write-back (ADR 0064): `POST /boards/:id/cards/:cardId/development/create-branch` and `.../create-pull-request`, each with `{ repositoryId }` naming one of the instance's connected repos (`GET /boards/:id/connected-repos`, D1 only), act through the instance App's installation token, so the author is `foxban[bot]` and the pull request body says "Opened by <name>". The branch is named from the task key; neither route links anything itself, the `create` and `pull_request` webhooks bring the result back onto the card like any other. Without an App they answer 503. Manual links: `POST /boards/:id/cards/:cardId/development/pull-requests` (`{ pullRequest: number | URL, repositoryId? }`, validated against GitHub, stored as a link with no key match) and `DELETE .../development/pull-requests/:repositoryId/:number` (records the tombstone key matching honours). Both write routes revalidate current board access, access-change state, the repo's installation and active card identity after preparatory GitHub reads and immediately before the external write. These checks reject changes completed during those reads; D1 authorization and a GitHub write cannot form one atomic transaction.
The Workers runtime is NOT Node: no `fs`, no `net`, no Node-only npm packages. Check compatibility before adding dependencies.

Attachment bytes live in the membership-gated `ATTACHMENTS` R2 bucket under `boardId/uuid` (for ordinary attachments) or `${destinationBoardId}/${transferId}/${attachmentId}` (for transferred attachments, where `transferId` is a safe 1–64-character Identifier and `attachmentId` is a UUID); the upload route canonicalizes the declared MIME type, registers a one-hour provisional lease in that board's DO, writes R2, and returns the authoritative type/size for `attachment.create` to claim. Exact PNG/JPEG/GIF/WebP metadata is served inline; every other stored or missing type is forced to `application/octet-stream` with `Content-Disposition: attachment` and `nosniff`. Explicit attachment deletion enqueues its R2 key through a DO SQLite trigger, then the shared alarm deletes the object, records a permanent terminal tombstone (setting `deleted_at` and `reason = 'deleted'`), and reschedules after failures. Individual card deletion and populated column deletion instead archive cards and preserve their attachment metadata and blobs until retention expiry. Ordinary attachment publication (`attachment.create`) transactionally validates that an exact matching cleanup lease by `object_key` exists in `attachment_cleanup`, is in `'staged'` state, is unexpired (`delete_after > now`), and is unclaimed and not tombstoned (`claim_token IS NULL AND deleted_at IS NULL`) before inserting metadata; missing, expired, claimed, or tombstoned leases reject the transaction before any write. The DO distinguishes an **idle tombstone state** (`deleted_at IS NOT NULL`, `reason = 'deleted'`, retained `claim_token`, `delete_after = 0`) from an **explicit redelete tombstone state** (`delete_after = now` or bounded retry `delete_after = retryAt`). Idle tombstones are excluded from alarm queries and due work (`WHERE deleted_at IS NULL OR (deleted_at IS NOT NULL AND delete_after > 0)`), preventing alarm loops. When global reconciliation (`reconcileAttachmentObjects` via `RECONCILE_ATTACHMENTS_PATH`) observes an exact unowned R2 object key matching an existing tombstone—such as an authorized pre-delete PUT that completed late after lease expiration or tombstoning—it transitions the row to the due redelete state (`delete_after = now`, `reason = 'deleted'`) and triggers alarm drain to re-delete the object bytes. Successful R2 deletion returns the row to the idle tombstone state (`delete_after = 0`, alarm null); deletion failure retains the claim fence and reschedules with a bounded retry delay (`delete_after = retryAt`, where `retryAt = now + 60_000`), scheduling the alarm at `retryAt`. Throughout both idle and redelete/retry states, the publication and staging fence is continuously maintained (`deleted_at IS NOT NULL`, `claim_token IS NOT NULL`, `reason = 'deleted'`); staging (`STAGE_ATTACHMENT_PATH`), import (`CARD_TRANSFER_IMPORT_PATH`), and ordinary publication (`attachment.create`) reject any tombstoned key with HTTP 409 Conflict. Fresh uploads and transfers generate fresh non-reusable keys (with UUID attachment IDs and safe 1–64-character Identifier transfer IDs). Tombstones persist for the lifetime of the board DO; deleting a board via `/internal/board/delete` purges the R2 key prefix and board-content rows, retaining a durable deleted marker and transfer outcomes for recovery (ADR 0061). Attachment reconciliation remains available to collect writes that finish after deletion.

### Authenticated MCP (`apps/api`)

`/mcp` is a stateless Streamable HTTP endpoint served by the existing Worker. Bearer credentials are independent of browser sessions and carry an explicit current user, stable board-id allowlist, closed scopes (`boards:read`, `tasks:write`, `comments:write`), expiry and revocation state. D1 stores only the SHA-256 token digest and management metadata. Every tool callback reloads the credential, user, scope and current board authorization; admin access never widens the credential.

Signed-in users manage their own credentials at `/mcp-server`. The page lists metadata through cursor pagination and issues or revokes credentials through the session-only `/me/agent-credentials` routes. A raw token exists only in page-local reveal state after the successful POST response: it never enters TanStack Query, browser storage, URLs or browser-test artifacts. During that reveal the user may copy the token alone, a generic `mcpServers` JSON configuration, or a VS Code `servers` JSON configuration; both configuration payloads are built only for the clipboard and embed the current-origin endpoint plus bearer token. An ambiguous response warns the user to inspect and revoke metadata rather than retrying issuance automatically.

Thirteen strict tools expose bounded board/task reads, task creation, title/description update, task move, linked-subtask completion/reopening (a move to the completed or starting column), top-level comment creation, and ordinary label definition/assignment management. Board and task reads page label definitions and exact card-label join IDs; `status:*` remains only a naming convention. The strict `get_board` column output carries `starting` and `completed` booleans; both are false on every column of a board with fewer than two columns. Board content remains exclusively in BoardDO SQLite. Internal typed POST routes perform bounded reads or the nine narrow commands; callers cannot submit arbitrary WebSocket messages or trusted headers. MCP and browser mutations share domain guards, transactional apply/activity behavior and ordered WebSocket fan-out.

Each mutation carries a caller UUID `operationKey`. BoardDO schema v23 stores a receipt keyed by credential and operation key, bound to actor, operation and canonical input hash in the same transaction as the mutation and committed result. Exact retries return the historical result without applying or broadcasting again. Receipts remain until board deletion; authorization is rechecked before receipt lookup.

### BoardDO

Uses the WebSocket Hibernation API — `state.acceptWebSocket(ws)` with `webSocketMessage` / `webSocketClose` handlers — NOT the legacy `ws.addEventListener` pattern. Idle boards must be able to hibernate; this is the cost model.

All board mutations (create/move/edit card, etc.) go through the DO, never D1. The DO applies each mutation to its SQLite storage, then broadcasts the change to all connected sockets. Board destruction is handled through private internal POST `/internal/board/delete`: it durably marks the board deleted, atomically clears content and queues, closes all connected WebSockets with code 1000 ("board deleted"), and paginates and deletes R2 objects under the board's key prefix. Schema, policy metadata and transfer receipts survive so identity-bound settlement can finish after deletion or restart; ordinary board access stays terminally refused. Attachment reconciliation still collects late uploads (ADR 0061).

### PresenceDO

One global hibernating Durable Object routed via `PRESENCE_DO.idFromName("global")`. Uses the WebSocket Hibernation API exclusively. Authenticated clients connect via `GET /presence/ws` with their browser's detected IANA timezone. The Worker derives the user's effective timezone from their saved `users.timezone` D1 preference override or the query parameter, validates it against IANA standards, and forwards to the global DO.

Presence is app-wide: a user is considered online as long as at least one tab has an open presence socket. When all sockets for a user close, `last_seen_at` is stamped in SQLite and an offline update is broadcast. Presence state is strictly partitioned from BoardDO card/column data.
### Shared (`packages/shared`)

Zod schemas + TypeScript types for Board, Column, Card, and the WS message protocol. Single source of truth for types. Also home to Markdown attachment utilities in `attachment-description.ts`:
- `removeAttachmentReferences(markdown, boardId, attachmentId)`: parses with `mdast-util-from-markdown` plus GFM extensions and splices source by node offsets, preserving all unrelated bytes (ADR 0035).
- `rewriteAttachmentUrls(markdown, sourceBoardId, destinationBoardId, attachmentIds)`: tracks exact parser-emitted token offsets (`resourceDestinationString` and `definitionDestinationString`) to remap source board attachment URLs to destination board URLs during card transfers, handling code backticks, inline brackets, entity encodings, and angle brackets cleanly without bracket-counting heuristics.

## Data model

### D1 (global data)

Tables: `users` (id, email, name, password_hash, created_at, github_login, github_user_id, timezone, avatar_version), `sessions`, `boards` (id, name, board_key, owner_id, icon, color; no repository: repos belong to the instance), `board_members`, `github_app` (the single instance GitHub App row: app_id, slug, client_id and the three sealed secrets), `github_repos` (the instance's connected repos: repo_id, installation_id, full_name, is_private, connected_at; repo identity only, no card data), `github_pr_routes` (repo_id, pr_number, board_id: which boards link a pull request; pointers only, no card data), `github_branch_routes` (repo_id, branch_name, board_id: which boards link a branch; pointers only, no card data), `github_backfill_queue` (repo_id, queued_at, run_after, attempts: repos waiting for backfill; no card data), `avatar_leases` (user_id TEXT, version TEXT, expires_at INTEGER, PRIMARY KEY (user_id, version)). Board appearance uses shared closed enums and migration defaults (`square-kanban` / `slate` for existing rows); card/column data is NEVER stored in D1. Admin board access is an authorization bypass rather than a row in `board_members`. `users.timezone` stores the user's optional explicit IANA timezone preference (null means automatic/browser timezone). `users.avatar_version` stores the user's uploaded-avatar version, with GitHub and initials fallback. User avatar publication uses atomic live-avatar-lease CAS consumption in a multi-statement D1 batch.

### PresenceDO SQLite (presence state)

Global presence metadata stored in `presence(user_id TEXT PRIMARY KEY, last_seen_at INTEGER, timezone TEXT)`. Not board state; tracks last seen timestamps and latest effective timezone for each known user.
### DO SQLite (board state)

Per-board storage via `ctx.storage.sql`. Migrations run idempotently in the constructor / `blockConcurrencyWhile`:

- `columns(id TEXT PK, title TEXT, position TEXT, starting INTEGER NOT NULL DEFAULT 0, completed INTEGER NOT NULL DEFAULT 0)`; at most one column of each role, set together (schema v25 added the flags)
- `cards(id TEXT PK, column_id TEXT, title TEXT, description TEXT, position TEXT, task_number INTEGER UNIQUE, priority TEXT NOT NULL DEFAULT 'medium', task_type TEXT NOT NULL DEFAULT 'task', due_date TEXT NULL, subtask_done INTEGER NOT NULL DEFAULT 0, created_at INTEGER, updated_at INTEGER, archived_at INTEGER NULL, archived_column_title TEXT NULL)`; `archived_at IS NULL` means active. `subtask_done` was the child's own completion flag (schema v21). Since schema v29 it is never read for an active card, whose completion is derived from its column; an archived card keeps the value it had when it was archived. Schema v22 promotes every linked child to immutable `task_type = 'subtask'`; new subtask creation and linking write that type directly, and a subtask cannot be retyped or parent another subtask. The type survives archive, restore and transfer; unlink and the purge of a parent promote the child to `task`.
- `meta(key TEXT PK, value INTEGER)`; schema version (v29), `next_task_number` counter and `workflow_roles_explicit` (1 once the starting/completed columns were chosen); also stores `board_id` string for deterministic first-request recovery wake-up
- `attachments(id, card_id, file_name, content_type, size, object_key)`; `object_key` is internal and never enters the snapshot
- `attachment_cleanup(object_key TEXT PRIMARY KEY, attachment_id TEXT NOT NULL, reason TEXT NOT NULL, delete_after INTEGER NOT NULL, claim_token TEXT, claimed_at INTEGER, deleted_at INTEGER)`; an internal alarm queue and permanent tombstone registry, not board data; schema v18 added `claim_token` and `claimed_at` to enforce atomic non-overwriting claims and restart-safe same-token deletion retries; schema v19 adds `deleted_at` and index `attachment_cleanup_deleted_at` to record permanent per-object deletion tombstones (`reason = 'deleted'`, `deleted_at IS NOT NULL`) upon successful R2 deletion instead of deleting queue rows. Object keys are permanently non-reusable; overlapping collectors converge idempotently via `COALESCE(deleted_at, ?)` without removing the fence. Terminal tombstones distinguish an **idle tombstone state** (`deleted_at IS NOT NULL`, `reason = 'deleted'`, retained `claim_token`, `delete_after = 0`)—which is excluded from alarm queries and due work (`WHERE deleted_at IS NULL OR (deleted_at IS NOT NULL AND delete_after > 0)`), preventing alarm loops—from an **explicit redelete state** (`delete_after = now` or bounded `retryAt > 0`). When scheduled reconciliation encounters late authorized R2 bytes matching an exact tombstoned key, the DO explicitly transitions the row to a due redelete state (`delete_after = now`, `reason = 'deleted'`) and schedules alarm drain to re-delete the object while continuously retaining the publication and staging fence (`deleted_at IS NOT NULL`, `claim_token` non-null). Successful re-deletion returns the row to the idle tombstone state (`delete_after = 0`, alarm null), while deletion failure retains the claim fence and reschedules with bounded retry (`delete_after = retryAt`). All publication and staging remains rejected with HTTP 409 Conflict across both states. Tombstone rows grow monotonically without an automatic retention bound or TTL pruning as deleted distinct keys accumulate (finite 10GB per-DO cap eventually risks SQLITE_FULL, not automatic pruning; tombstones must never be TTL-pruned). Fresh uploads and transfers generate fresh non-reusable keys (with UUID attachment IDs and safe 1–64-character Identifier transfer IDs).
- `comments(id TEXT PK, card_id TEXT, author_id TEXT, parent_comment_id TEXT NULL, deleted INTEGER NOT NULL DEFAULT 0, body TEXT, created_at INTEGER, updated_at INTEGER)`
- `activities(sequence INTEGER PK AUTOINCREMENT, id, card_id, actor_id, detail_json, created_at)`; immutable per-card history, retained while archived and deleted with its card
- `card_transfer_locks(card_id TEXT PRIMARY KEY, transfer_id TEXT NOT NULL UNIQUE, destination_board_id TEXT NOT NULL, phase TEXT NOT NULL DEFAULT 'prepared', expires_at INTEGER NOT NULL, generation INTEGER NOT NULL DEFAULT 1)`; non-expiring source write fences freezing cards and child rows during transfer until terminal transition
- `card_transfer_operations(transfer_id TEXT PRIMARY KEY, card_id TEXT NOT NULL, destination_board_id TEXT NOT NULL, generation INTEGER NOT NULL, state TEXT NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL)`; durable transfer operation history tracking lifecycle states (`prepared`, `finalized`, `aborted`)
- `card_transfer_receipts(transfer_id TEXT PRIMARY KEY, source_board_id TEXT NOT NULL, card_id TEXT NOT NULL, task_number INTEGER NOT NULL)`; idempotent receipts keyed by transfer operation (not source/card pair), enabling repeated transfers between the same boards; `task_number = -1` indicates a terminal abort tombstone
- `mcp_operation_receipts(credential_id, operation_key, actor_id, operation, input_hash, result_json, created_at)`; durable BoardDO-local successful-operation fences retained until board deletion
- Triggers: `attachments_preserve_imported_object` deletes staged cleanup entries `WHEN NEW.object_key IS NOT NULL` on import (guarded by `AND deleted_at IS NULL`); `attachments_queue_object_delete` enqueues deleted attachment keys into `attachment_cleanup` with `ON CONFLICT(object_key) DO UPDATE SET reason = 'deleted', delete_after = 0 WHERE attachment_cleanup.claim_token IS NULL AND attachment_cleanup.deleted_at IS NULL`, preserving active in-flight claims and permanent tombstones. (The legacy `attachments_claim_staged_object` trigger was dropped in schema v18; ordinary publication is validated and consumed in `attachment.create`).
- First-request recovery wake-up: establishing board identity via HTTP headers automatically inspects expired `card_transfer_locks` and schedules deterministic alarm recovery via `scheduleAlarmAt(Date.now())` and `waitUntil(recoverExpiredTransferLocks)`.
- `card_github_pull_requests(card_id TEXT PRIMARY KEY, repository_id INTEGER NOT NULL, pull_number INTEGER NOT NULL, revision TEXT NOT NULL)`: the one pull request the per-board integration (ADR 0041) linked to a card by hand. Nothing writes it any more (ADR 0064) but it stays readable: the first development read of a card whose repo is connected adopts the row into `card_development_pull_requests` (the Worker reads the PR from GitHub and writes it back like a webhook), and until then it is retained through archive/restore, carried in the transfer bundle (`pullRequestAssociation`, re-minted at the destination) and deleted with the card aggregate.
- `card_development_branches(card_id, repository_id, name, repository, url, sha, message, committed_at, observed_at, PRIMARY KEY (card_id, repository_id, name))` (schema v27): development info (ADR 0064), one row per linked (card, branch) holding only the latest commit; written by `POST /internal/github/branch`, removed by a member's branch unlink, retained through archive, carried to the destination in a card transfer bundle (`developmentBranches`, no schema change), and deleted with the card aggregate on purge or when the card leaves in a transfer, and with the board.
- `card_development_pull_requests(card_id, repository_id, number, repository, title, state, url, updated_at, PRIMARY KEY (card_id, repository_id, number))` (schema v26): development info (ADR 0064), one row per linked (card, PR), written only by `POST /internal/github/pull-request` and read by `GET /internal/cards/:cardId/development`. It is retained through archive, carried to the destination in a card transfer bundle (`developmentPullRequests`, no schema change), and deleted with the card aggregate on purge or when the card leaves in a transfer, and with the board.
- Development info and card identity are read on demand through internal BoardDO routes, preserving BoardDO authority over card title and task numbers: `GET /internal/cards/:cardId/write-back` (id, title and task number of an active card, for the write-back routes), `GET /internal/cards/:cardId/development` (the card's pull requests and branches, plus the not-yet-adopted old links for the Worker), `GET /internal/development` (every active card's pull requests, for the card fronts) and the write routes above. The membership-guarded public routes are `GET /boards/:id/development`, `GET /boards/:id/cards/:cardId/development`, `GET /boards/:id/connected-repos`, the manual link and unlink routes (including the branch unlink) and the two write-back routes.
### Subtask families and independent status

A subtask is a full card linked by a `subtask` relation whose source is the parent (ADR 0019) and has its own stored column ([ADR 0067](decisions/0067-one-subtask-mode.md)); there is one mode on every board. `buildSubtaskHierarchy(cards, relations)` in `packages/shared/src/subtasks.ts` resolves the board's active cards and stored relations once per state change into `parentByChild`, `childrenByParent` (position-then-id order) and `rootByCard`. Both BoardDO (`activeHierarchyOf`) and the web reducer read that one implementation. Moving a parent or a child is one `card.move` and one card row; the rest of the family stays where it is. The board nests a child under its parent only while both sit in the same column, and progress counts every direct active child in any column.

Completion is derived: a card is done when it sits in the board's completed column (`subtaskDone` on the wire, computed from the column on every read; an archived card carries the value it had when archived). A board's `starting` and `completed` columns are set together. They follow the board's ends until an admin chooses: while `meta.workflow_roles_explicit` is not set, every `column.create`, `column.move` and `column.delete` recomputes them in the same transaction (leftmost column starting, rightmost completed, by position, none below two columns), moving no card, and the delete guard on role columns does not apply. The web reducer applies the same rule, so peers need no snapshot, and the snapshot carries `workflowRolesExplicit` so a client knows whether it applies. `workflow.configure` only changes the two roles, with expected-role preconditions, distinct existing columns and the transfer-lock fence; it moves no card, it makes the roles explicit (they then never drift when columns are added or reordered, and a role column needs a replacement before deletion), and it is not available to MCP. A board with fewer than two columns has no roles: new subtasks and converted checklist items join their parent's column, nothing counts as done, and neither `card.finish` nor the completion dialog applies. A new subtask starts in the starting column, or in the completed one when a done checklist item became it. 

The resolver ignores rather than repairs malformed stored data: self-links, edges with a missing endpoint, duplicate identical pairs, a child with more than one distinct parent, and every edge of a stored cycle are dropped from the derived forest. Nothing is deleted or hidden — a card without a usable parent is a root — and `relation.create` refuses new structural violations with `Invalid subtask hierarchy.` (one parent, live endpoints, no self-link, no duplicate pair, no cycle).

`relation.delete` promotes the child to `task` without moving it. `card.delete` archives the named card alone, with its own column and the server timestamp; its children stay active in their columns and the links remain, inactive while an endpoint is archived. `column.delete` archives exactly the cards stored in it, and its transfer fence covers exactly those cards. `card.restore` uses the submitted destination. Purging a parent promotes its surviving children to `task`.

**Conversion (schema v29).** One BoardDO schema step, `convertToIndependentSubtasks`, moved every board from the earlier inherited-placement mode, once, inside the schema transaction. A board that already had a starting column was left alone, and its roles became explicit (an admin had chosen them). Otherwise, with two columns or more, the leftmost column became starting and the rightmost completed; if the board held any card, active or archived, the roles became explicit too, and a board with no cards stayed automatic. Each active subtask was then placed by the legacy hierarchy (a subtask displayed in its topmost ancestor's column and was done when its stored `subtask_done` said so): a done child went to the completed column; any other child went to the column it was displayed in, except that one displayed in the completed column went to the starting column, staying open; a child with no parent the forest accepts (none, two, or a cycle) became a `task` and lost its incoming subtask links, while a child whose parent is archived kept its link (restoring the parent reattaches it) and was placed by its own data: done to the completed column, otherwise its stored column, or the starting column when that is the completed one. Moved cards were appended to the destination column's tail in their existing position order. Boards with fewer than two columns got no roles and kept each child in its parent's column. Archived cards were not touched. The legacy inherited-column rule survives only inside the migrations (`inheritedColumns`).

### Archived-card lifecycle

Deleting an active card stamps it, and only it, with a BoardDO server timestamp and its column title. Deleting a column stamps every active card stored in it with one shared timestamp before deleting only the column. An orphaned active card uses `"(deleted column)"` as its former title. Archived cards and every card-owned row remain in BoardDO SQLite, are read-only, and appear separately from active cards in snapshots. A member restores or permanently purges each archived card explicitly.

One idempotent Durable Object lifecycle owns both manual/retention archive purges and attachment cleanup. The alarm selects at most 1000 cards whose rolling `90 × 24`-hour window has elapsed; `card.purge` selects one archived id. Both use the same transactional dependent-row cascade, broadcast `archive.purged`, drain newly queued R2 keys, and leave the alarm scheduled for the earlier of the next attachment cleanup or archive expiry.

### Ordering

Fractional indexing with string position keys (the `fractional-indexing` npm package). Moving a card writes ONE row, never renumbers siblings.

## WebSocket protocol

JSON text frames validated with the shared Zod schemas from `packages/shared` (`ClientMessageSchema`, `ServerMessageSchema`; entities `Column`, `Card`). camelCase on the wire; snake_case only inside the DO's SQL.

The authenticated, membership-checked Worker overwrites internal board/user headers and `x-foxban-can-manage-columns` before forwarding a board upgrade. It derives the capability from the already-authorized board's `ownerId` and authenticated user's `ADMIN_EMAILS` verdict, never from client headers or mutation fields. BoardDO validates identity and stores `{ userId, boardId, canManageColumns }` in the hibernating socket attachment; only the exact fresh header value `"true"` grants the capability, with missing or other values stored as false. Activity actors remain server-attributed.

After identity and message-schema validation, BoardDO gates exactly `column.create`, `column.rename`, `column.move` and `column.delete`, before archived/locked-card checks, alarm scheduling, activity derivation or transaction entry. Boolean true continues through the existing mutation path. Boolean false returns a sender-only, mutation-correlated error (`"Only the board owner or an admin can change columns."`) and keeps the socket open for card collaboration. A denial changes no board state, archive, activity or alarm and emits no successful mutation or lifecycle broadcast.

A missing or non-boolean capability in an existing socket attachment instead returns the correlated error `"Reconnect to change board columns."` and closes with code `1012`. The client rolls back the rejected operation; reconnect re-derives authority and the user must deliberately retry the operation, with no automatic replay. The existing bounded reconnect budget and manual connection **Retry** remain in force. Authority is connect-time scoped, like membership/session checks: no per-mutation D1 lookup or live role-revocation machinery. This internal capability adds no database field, public snapshot property or role, and does not change wire shapes or the public realtime protocol version.

Entities:

```ts
Column = { id: string, title: string, position: string,
           starting?: boolean, completed?: boolean }  // the BoardDO always sends both
Card   = { id: string, columnId: string, title: string, description: string,
           position: string, taskNumber: number, assigneeId: string | null, priority: Priority,
           taskType: TaskType, dueDate: string | null, subtaskDone: boolean,
           createdAt: number, updatedAt: number }
ArchivedCard = Card & { archivedAt: number, archivedColumnTitle: string }
Comment = { id: string, cardId: string, authorId: string, parentCommentId: string | null,
            deleted: boolean, body: string, createdAt: number, updatedAt: number }
Activity = { id: string, cardId: string, actorId: string,
             sequence: number, createdAt: number, detail: ActivityDetail }

Client → server — discriminated union on `type`; every message carries a client-generated `mutationId` (uuid). Clients also generate entity `id`s (`crypto.randomUUID()`) and `position` keys (fractional indexing, client side); the DO trusts them (LWW between two trusted users, ADR 0007):

```
{ type: "column.create", mutationId, id, title, position }
{ type: "column.rename", mutationId, id, title }
{ type: "column.delete", mutationId, id }            // DO archives its active cards
{ type: "card.create",   mutationId, id, columnId, title, position, taskType?, priority?, assigneeId? }
{ type: "card.update",   mutationId, id, title?, description? }
{ type: "card.move",     mutationId, id, columnId, position }
{ type: "card.delete",   mutationId, id }
{ type: "card.retype",   mutationId, id, taskType }
{ type: "card.restore",  mutationId, id, columnId, position }
{ type: "card.purge",    mutationId, id }            // archived ids only; permanent
{ type: "subtask.create", mutationId, id, parentCardId, relationId, title, position, checklistItemId? }
{ type: "comment.create", mutationId, id, cardId, authorId, parentCommentId, body, createdAt }
{ type: "comment.update", mutationId, id, body, updatedAt }
{ type: "comment.delete", mutationId, id }

Server → client:

- `{ type: "snapshot", workflowRolesExplicit: boolean, columns: Column[], ..., cards: Card[], archivedCards: ArchivedCard[], activities: Activity[] }` — sent immediately after accept; entity arrays are unordered, active and archived cards are separate, and card activity is presented by `sequence`.
- Mutation broadcast — the client message forwarded **verbatim** (byte-for-byte) to ALL sockets, sender included; the sender reconciles by `mutationId`.
- `{ type: "card.numbered", mutationId, id, taskNumber }` — server-only authoritative reconciliation sent immediately after accepted verbatim `card.create` and before any activity frame.
- `{ type: "activity.recorded", mutationId, activities: Activity[] }` — server-only, sent after the matching mutation when the accepted change produced history.
- `{ type: "cards.archived", mutationId, cards: ArchivedCard[] }` — server-only authoritative reconciliation sent after the matching verbatim `card.delete` or `column.delete`.
- `{ type: "archive.purged", cardIds: string[] }` — server-only authoritative reconciliation for retention alarms and accepted `card.purge` mutations.
- `{ type: "github.invalidated", scope: "card", cardId: string, revision: null }`: server-only, emitted after an accepted webhook write, manual link or unlink to a card's development info. A hint, never data: the client marks the development caches stale and lets the next authoritative read install the truth. There is no client-side variant and no optimistic replay. (The repository scope, and card-scope hints that carried a link revision, ended with the per-board integration; `revision` stays in the frame only so older clients still parse it.)
- `{ type: "error", mutationId: string | null, message: string }` — sender only; `mutationId` is null when the frame was unparseable.

### Realtime protocol versioning and reconnection lifecycle

- Both board (`/boards/:id/ws`) and presence (`/presence/ws`) WebSocket URLs require query parameter `?realtimeVersion=10` matching `REALTIME_PROTOCOL_VERSION = "10"`. Version `"4"` made `subtask` an immutable one-level type; `"5"` made parent deletion archive its complete active subtask family; `"6"` enriches `card.create` with optional `taskType`, `priority` and nullable `assigneeId`; `"10"` removes the inherited subtask mode (`subtask.complete` is gone and `workflow.configure` loses its `migration` field). Older clients strictly parse mutation broadcasts and cannot safely consume the enriched frame, so previous versions are rejected explicitly.
- Development info (ADR 0064) adds no frame and no version: an accepted webhook write reuses the card-scope `github.invalidated` hint, which every deployed client already parses, and the client answers it with reads of `GET /boards/:id/cards/:cardId/development` and `GET /boards/:id/development`. A future frame that carries development data itself would need a bump.
- The Worker validates `realtimeVersion` after authentication and board membership, but before acquiring a Durable Object stub. Incompatible or missing versions receive HTTP 409 `{ error: "realtime client update required" }`, preventing obsolete client bundles from querying DO SQLite storage.
- Connection health is defined by a validated snapshot AND 10 seconds of continuous connection (`STABLE_CONNECTION_MS = 10_000`), not transport `onopen`. Retry backoff and failure counts reset only after surviving open for 10 seconds following a valid snapshot.
- Unsynchronized or unstable closes (including unparseable/unsupported frames dropped by the client or immediate disconnects following snapshots) trip a circuit breaker at 3 consecutive failures (`MAX_FAILED_SYNCHRONIZATIONS = 3`), halting reconnection attempts. Unparseable board frames log a sanitized warning without raw payloads, drop immediately, and count toward the breaker. For an already-loaded board page, the UI keeps the board page, active card modals, and drafts mounted, displaying **Could not connect.** with a manual **Retry** action that restarts the 3-attempt budget; only an initial connection failure before a snapshot displays the full-page failure view. Presence reconnection stops silently with one console warning.
- Live-socket timeout of an authored operation requiring authoritative settlement verification (`mutationSubscribersRef.has(mutationId)`) triggers a transport close with code 4000 (`"authored operation timeout resync"`), prompting an immediate reconnect and fresh snapshot fetch. Ordinary instant mutations (such as column moves, label toggles, drag-and-drop) or attachment deletions do not close the transport on timeout.
- Closes that occur after achieving 10 seconds of stable connection continue bounded exponential backoff reconnection and require re-establishing stability on reconnect.
- Operational analytics diagnostics use Cloudflare GraphQL datasets `durableObjectsPeriodicGroups` (summed `rowsRead`, `rowsWritten`, `outboundWebsocketMsgCount`) and `durableObjectsInvocationsAdaptiveGroups` (summed `requests`, `errors`), grouped by object name, hour, and invocation status/type.

DO semantics: archived-target rejection runs before activity derivation. Pre-mutation activity derivation, the mutation, immutable activity inserts, and any card lifecycle result occur in one synchronous SQLite transaction. `card.create` accepts optional `taskType` (`epic`, `spike`, `task` or `bug`), optional `priority` (the shared Priority enum), and optional nullable `assigneeId` (Identifier or null). Omission preserves defaults: `task`, `medium` and null. Subtask is not a `card.create` type; it remains parent-created through `subtask.create`. After validating the destination column, `card.create` passes all selected fields to the shared `insertCard` path: one card INSERT binds `task_type`, `priority` and `assignee_id` alongside the title, placement and allocated task number. It records one `card.created` activity, not follow-up property-edit history, and retains the existing `card.numbered` frame. Creation writes board data only to DO SQLite, with no new migration or D1 board-data write. Archived cards reject every card-owned mutation except `card.restore` and `card.purge`; board-scoped `label.delete` still removes its definition and joins. `subtask.create` carries its own precise refusal (`Parent task is unavailable.`) and remains covered by the transfer fence. `subtask.create` writes the child (ordinary priority/assignee defaults, immutable subtask type, column from the workflow roles — the starting column, or the completed one for a done converted item, or the parent's own column on a board without roles) and the `subtask` relation in the same transaction, then returns the existing `card.numbered` frame and records `card.created` plus two-sided `relation.added` history (with `checklist.deleted` for a conversion) — all from one `insertCard`/`allocateTaskNumber` path shared with `card.create`, never a second counter. A deliberate retry that repeats the exact child, parent and relation is an idempotent replay: it returns the stored task number and writes no row and no history, while any other collision with those ids is refused with `Subtask identity is already in use.`. Destination column existence is validated transactionally in `card.create` and `card.move`: targeting a non-existent column throws an error and rejects the mutation before creation allocates a task number, allowing the client to roll back rather than stranding active cards in deleted columns (mutations matching no row remain accepted silent no-ops). `card.delete` archives the active card alone. `card.purge` permanently cascades only an archived row; an active or missing id is an accepted no-op, so a stale archive client cannot destroy active data. Manual and retention purges share the same dependent-row cascade, attachment trigger, `archive.purged` frame and R2 cleanup drain. Cross-board transfer preserves the source card's `taskType`.

### Independent subtasks (ADR 0057, ADR 0067)
BoardDO schema v25 added explicit starting/completed column roles; schema v29 converted every board to them and removed the inherited mode (see [Subtask families and independent status](#subtask-families-and-independent-status)). Every card uses its stored column and derives completion from that column; same-column children nest, and progress counts all direct active children. Parent moves/archive leave children in place, restore chooses a destination, and unlink/purge promotes detached children. The realtime protocol version persists in hibernating attachments and fences incompatible sessions (version 10 is current). MCP moves accept any task; completion shortcuts move the child to the completed or starting column. The conversion is a one-way data change: BoardDO point-in-time recovery is the rollback, restoring data before the old binary.

### Explicit independent-family completion

See [ADR 0059](decisions/0059-explicit-family-completion.md). A parent entering the explicitly completed column with active unfinished descendants opens an accessible choice before any mutation. `card.finish` in realtime protocol 9 explicitly chooses parent-only or the full unfinished family. Its expected parent placement and full descendant placement/parentage guard concurrent changes. BoardDO validates the exact move set and commits every placement plus activity in one SQLite transaction; already completed and archived descendants are excluded from movement. Ordinary `card.move` and all existing MCP moves remain single-card operations. Reopening never reopens children. No schema migration accompanies this change.
