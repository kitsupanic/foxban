# Web (`apps/web`)

Part of [architecture](../architecture.md).

Vite + React SPA with TanStack Router + TanStack Query; drag-and-drop via dnd-kit.

TanStack Query owns server state:

- Board state (columns, cards, comments; no card history) arrives exclusively over the WS: the snapshot on connect populates the `['board', boardId]` cache (board content has no REST endpoint); REST covers auth, profile/account, board metadata (`GET /boards/by-key/:key`, `GET /boards`), and members.
- Authoritative base-state rebase & production `BoardReconciler`: `useBoardSocket` delegates mutation queuing, server message reconciliation, and optimistic rebase directly to `BoardReconciler` (`createBoardReconciler`), the single production transition implementation shared verbatim between socket runtime and regression suites (`apps/web/test/reconciliation.spec.ts`), eliminating test-model duplication. The reconciler maintains `baseState` as authoritative server state; accepted mutation broadcasts (both peer updates and own echoes) apply in server order directly to `baseState`. Own echoes retire their rollback timers and pending map entries. Remaining optimistic mutations in `pending` rebase in send order over `baseState` (`syncCache`), guaranteeing convergence and server-order last-write-wins (LWW) without skipping echoes.
  Coverage is two-layered: the deterministic-logic layer (`apps/web/test/reconciliation.spec.ts`, run service-free with no browser or local stack) drives the production reconciler primitives directly over fixed frame orderings, while the real-runtime layer (`apps/web/e2e/sync.spec.ts`) proves the same behavior through live services — two signed-in browser contexts on one board, a peer `column.rename` accepted by the live BoardDO between a client's optimistic rename and its own outbound frame, convergence of both clients and of a freshly opened third client's snapshot on the server-ordered last write, over a single uninterrupted socket (one snapshot, no reconnect).
- Optimistic rollback removes the rejected or timed-out mutation and rebases the remaining pending mutations over authoritative server state. No inverse callbacks are constructed or stored; peer changes and accepted lifecycle events remain authoritative.
- Drag-and-drop performs an optimistic cache update, sends the mutation over WS, and rolls back if the DO rejects or the echo never arrives (timeout). Card bodies own drag measurements; families remain stationary while a compact portaled preview and explicit boundary marker show the move. `card-drop.ts` orders direct same-status siblings or destination roots, normalizes descendant targets to displayed peer boundaries, bounds each new key by the next key in the whole column so it never ties a non-peer row, and preserves one-row fractional moves. Pointer collision excludes clipped canvas regions; keyboard navigation follows logical peers/statuses and includes the tail slot (ADR 0058).
- Attachment lifecycle: `apps/web/src/lib/attachments.ts` (`useBoardAttachments`, one per board in `BoardView`) owns owner tracking, pending and confirmed deletions, the description mount seed, deleted-embed cleanup of open drafts (ADR 0035) and the upload (checks, POST, then `attachment.create` settled as an authored operation, ADR 0069). `useBoardSocket` feeds it through a generic `BoardEventObserver` (`snapshot`, `message`, `sent`, `resolved`) and keeps no attachment state itself; `CardModal` reads it with `useAttachmentView`. Attachment delete is an instant mutation in `board-commands.ts`.
- Board commands: every instant (non-authored) mutation goes through `apps/web/src/lib/board-commands.ts` (`useBoardCommands`). It mints the mutation and entity ids, builds the message, picks the fractional key and returns `"sent" | "not-sent" | "no-op"`. A move with no position (a status change or subtask completion) lands at the tail of its displayed peers by the same rules as `card-drop.ts`. `moveCard` is the only `card.move` sender: a card with open subtasks entering the completed column returns `needsFinish` instead of sending, and `BoardView` opens the family-finish dialog. Authored operations keep their own builders and borrow only the `placeNew*` keys.
- Card sections: `CardModal` is layout plus wiring. Each section that holds drafts has a React-free core with a thin hook in `apps/web/src/lib` — `card-draft.ts` (title, description, Save), `comment-thread.ts` (comments, one-level replies, edits), `checklist.ts` (checklist text), `subtask-composer.ts` (subtask composer and checklist conversion) — each creating its authored operations on the modal's scope and tested service-free in `apps/web/test`. Presentational sections live in `CardActivity`, `CardChecklist`, `CardSubtasks`, `CardRelations` and `CardLabels`. `CardModal` keeps the scope, the close guard and Escape ladder (ADR 0020), the URL-backed view and attachment viewer (ADR 0021), and the instant metadata fields.
- Missing-column rejection: `card.create` and `card.move` validate that the destination column exists in DO SQLite storage; if the destination column was deleted concurrently, the DO rejects the mutation, triggering optimistic rollback rather than stranding active cards in non-existent columns. (Mutations targeting missing cards remain accepted silent no-ops).
- Upload insertion conflict behavior: `MarkdownEditor` tracks in-flight image uploads via dynamic anchors (`computeEditRange`, `adjustAnchorOffset`). User typing during an active upload adjusts anchor boundaries. If the user edits text within a selected range while an upload is pending, `rangeEdited` triggers conservative insertion at `boundedEnd` rather than replacing text, preserving all user edits and deterministically positioning the caret.
- Strict SVG clipboard conversion: SVG clipboard paste is opt-in for card descriptions only (`allowSvgPaste` on `MarkdownEditor`, passed by `DescriptionEditor`); comment/reply editors, the toolbar Image picker, general attachment uploads, and server download-only isolation (`Content-Disposition: attachment`) remain unchanged. Clipboard payloads are selected in priority order (SVG file with MIME `image/svg+xml` or empty-MIME `.svg`, SVG MIME string, whole `text/plain` SVG document, then supported raster files; prose containing SVG or fenced code remains native text). Conversion runs client-side via `compressImage(..., { rasterizeSvg: true })` producing a single WebP attachment (quality 0.8, max edge 2048, no upscaling), rejecting DOCTYPE/entity declarations, parsing in a detached XML DOM, validating SVG root and SVG namespace (re-parsing with standard SVG namespace if omitted so children inherit identity), calculating dimensions/viewBox (synthesizing a viewBox when downscaling unviewboxed SVGs to prevent clipping), enforcing root CSS dimension caps with `!important`, decoding through `HTMLImageElement` with an object URL and 10s timeout, and blocking script/external network execution. Conversion strictly requires `image/webp` output and never falls back to original SVG, PNG, or vector bytes on error.
- Retained description editor & pending upload lifecycle: `DescriptionEditor` mounts `MarkdownEditor` once on first edit and retains the instance across Preview/Edit toggles until card disposal (`active` prop inerts toolbar, textarea, and trailing controls without unmounting in-flight state). `CardModal` acquires `descriptionUploadingRef` synchronously before starting async conversion, guarding Save and Ctrl/Cmd+Enter and exposing inline accessible status (`role="status"` "Converting and uploading image…") and busy notices (`role="alert"`) that survive into preview mode. Preview/Escape functions as preview rather than cancellation; completion while previewing updates rendered text without stealing focus to hidden controls; and card disposal invalidates pending operations via a liveness ref to prevent late draft/focus mutations without deleting already-published attachments. Upload caret restoration waits for the exact controlled value in a layout effect: an animation frame can run before the new value commits and clamp the selection against the old text. The one-shot pending selection is cancelled by native/toolbar edits or inactive/read-only state, applies only to the same connected textarea and never changes focus.
- Stable Markdown renderer identity across viewer navigation: the `react-markdown` `components` maps (`standardMarkdownComponents`, `youtubeMarkdownComponents` in `MarkdownEditor.tsx`) are module-level constants rather than per-render object literals, and the embedded-image renderer (`StableMarkdownImage`) reads its preview index and open callback from `MarkdownPreviewContext` instead of props. Because the component types are referentially stable, opening or closing the URL-backed attachment viewer (`?attachment=<id>`) re-renders the rendered description or comment without remounting its subtree, so the embedded image button that invoked the viewer keeps its DOM identity and remains a valid focus-return target.
- Acceptance-aware authored settlement & locked-editor lifecycle: `ws.send` is an unconfirmed network transmission, not operation completion; the server echo or snapshot is authoritative. Authored operations (`card.update` from Save, `comment.create`, `comment.update`, `comment.delete`) register with `notifyMutation` in `useBoardSocket`. The mutation status lifecycle spans `accepted`, `rejected`, `timeout`, `uncertain`, and `verified-retry`. While an authored operation is pending or uncertain, its specific editor lane locks read-only (`readOnly` and disabled controls), displaying submitted text byte-for-byte to prevent divergent drafts, while unrelated composer lanes remain editable. On live-socket timeout of an authored operation (`mutationSubscribersRef.has(mutationId)`), `useBoardSocket` rolls back the local optimistic mutation and initiates an authored-only resync by closing the transport (`ws.close(4000, "authored operation timeout resync")`); ordinary instant mutations or attachment deletions do NOT close the transport. Upon receiving a snapshot, the reconciler applies the snapshot, and the TanStack Query cache is updated (`queryClient.setQueryData`) *before* notifying mutation subscribers. If the snapshot contains the mutation, it settles as `accepted` without entity duplication; if verified absent, it settles as `verified-retry`, unlocking the editor with the exact raw draft for explicit user retry or discard. Raw editor text is distinct from normalized wire body. Reconnects and disconnects mark pending authored operations `uncertain`, disabling retries until snapshot verification. There is no automatic resend, no offline queue, and no toast notification.
- Acceptance-aware checklist text: checklist creation and inline text edits use the existing mutation settlement subscriptions. Shared title validation runs before transmission, and exact raw drafts survive rejection, dropped sends and verified absence. Pending or uncertain submissions lock only their own lane and remain mounted until authoritative acceptance or snapshot verification. Unsent checklist text participates in the modal close guard; peer-deleted edits offer explicit save-as-new or discard recovery. Checkbox toggles and deletion remain instant mutations (ADR 0062).
- Acceptance-aware creation dialogs: `BoardView` allocates one entity id and mutation id per attempt and calls `subscribeMutation` before `sendMutation` for `card.create` and `column.create`. Only `accepted` closes the dialog, whether delivered by the server echo or authoritative snapshot verification; the optimistic cache is never acceptance evidence. `isMutationPresentInBoardState` checks a column by id and a card by id in active **or archived** cards, so later peer edits or archival do not trigger duplicate creation. A false send retires tracking and leaves the draft editable with "Not connected — changes won't send."; a rejection retires tracking and retains the draft with the server error. `timeout` and `uncertain` keep fields, submit and dismissal locked with "Checking whether creation completed…", using the existing socket resynchronization path. An authoritative snapshot that verifies absence emits `verified-retry`, retires the attempt and unlocks the retained draft with "Creation was not confirmed. You can try again." for explicit retry, never automatic resend. Terminal connection failure exposes a connection **Retry** outside the disabled form fieldset, still usable while creation is pending. Terminal attempts and unmount unsubscribe and retire tracking.
- Reconnect logic & loaded board page durability: exponential backoff; on reconnect, request a fresh snapshot — never try to replay missed events. Discard pending timers on reconnect; no localStorage for board data — the server is the source of truth. Once an initial snapshot has loaded, terminal connection failure (circuit breaker tripped after 3 unsynchronized failures) preserves the mounted board page, open card modals, and in-progress drafts in memory, exposing an actionable `Retry` callback in the board header and modal footer that resets the attempt budget, rather than unmounting the board page. Only an initial connection failure prior to any snapshot displays the full-page failure screen. The board socket and the app-wide presence socket share one backoff and failure budget (`planBoardReconnect`, `STABLE_CONNECTION_MS` in `access-attempt.ts`). A short network drop can spend that budget, so a loop that stopped (not one denied) starts over when the window fires `online` or the document becomes visible again: the board socket through its `retry()` path, presence by resetting its counters and reconnecting. `pendingSentMutationsRef` entries that a reconnect snapshot reports `uncertain`/`verified-retry` are dropped once nothing subscribes to them (instant mutations), so the map does not grow.
- Render cost on large boards: `BoardView` builds one `BoardIndex` per board state (`buildBoardIndex` in `apply-mutation.ts`: a card-by-id map and per-card checklist/attachment/comment counts, relations and labels) and passes it to `ColumnView`/`getCardFaceProps`, so a card face and the column layout read aggregates instead of scanning the board's flat arrays per card. `columnRootCards` and `boardAncestors` take the card map. `hasYouTubeVideo` caches by description string (small capped module-level map).
- Content-Security-Policy: `apps/web/public/_headers` (copied to `dist/`, honoured by Workers static assets) restricts `img-src` to this origin, `data:`, `blob:` and GitHub avatars (`github.com` redirects to `avatars.githubusercontent.com`); no other directive is set. `MarkdownEditor` renders a Markdown image from any other origin as a plain link (or its alt text inside a link), so a blocked image stays reachable. `hasYouTubeVideo` walks paragraphs at any depth (quotes, loose list items), matching the `p` renderer's embeds; a paragraph directly inside a tight list item does not count, because `mdast-util-to-hast` unwraps it before the renderer sees a `<p>`.
- Card history is not in board state ([ADR 0073](../decisions/0073-per-card-activity-loading.md)). The card modal reads `GET /boards/:id/cards/:cardId/activity` (`cardActivityQueryOptions`, key `['card-activity', boardId, cardId]`); the creator and assignee history it shows come from the same read, so they appear when it lands. A live `activity.recorded` frame merges into that cache by id in sequence order (`recordActivities`; a card with nothing loaded refetches, so a read in flight cannot miss it), a reconnect snapshot marks every loaded history stale (`invalidateCardActivity`), and the key is a board-private cache key removed on a confirmed access denial.
- Development info reads nothing on a timer ([ADR 0064](../decisions/0064-instance-github-app-webhook-development-info.md)). Card fronts show a compact pull request badge from one board-wide read, `GET /boards/:id/development` (`boardDevelopmentQueryOptions`): the badge names the pull request still in play (open, then draft, then merged, then closed; the most recently updated within a state) and a count when there are several. The card's Development section reads `GET /boards/:id/cards/:cardId/development` (`cardDevelopmentQueryOptions`) and offers a repository picker fed by `GET /boards/:id/connected-repos`, Create branch and Create pull request in the picked repo, a manual link by number or URL, and an unlink button on each pull request and each branch. A card-scope `github.invalidated` hint on the board socket, and a reconnect snapshot, mark `card-development` and `board-development` stale (`invalidateDevelopmentQueries`) and the next read installs the truth; there is no interval, no focus or visibility refresh and no per-viewer GitHub call. Both queries are board-private cache keys, removed on a confirmed access denial like the rest. A card's link draft (`usePullRequestLink`) lives in the card modal so the modal's dirty guard and Escape ladder see it; linking the same pull request twice changes nothing, so a failed attempt is simply submitted again.
- Deferred focus restoration yields to a live keyboard owner, and resolves its target at frame time: `restoreFocusSoon` (`apps/web/src/lib/focus.ts`) is the single helper for focus that must return to a trigger after an overlay closes or an inline editor commits. It accepts either an element or a resolver, and a resolver runs **inside** the single animation frame — so a card whose node was replaced or re-parented while the modal was closing (a peer move putting it in another column) still regains focus, because the lookup happens after the move rather than before the frame. The one-frame delay and the `isConnected`/`inert` guards are kept, and the restore proceeds only while focus has fallen back to the document: if anything else has taken the keyboard in the meantime (a user or test keystroke landing in another field), the restore is abandoned instead of stealing focus. Callers are the column rename commit/cancel path (`ColumnView`) and the overlay-close restores in `BoardView` (card modal, column delete alert, archived cards, member drawer, mobile filter sheet); `closeCard` is the site that passes a resolver, the rest pass the captured element. Board-level shortcuts depend on this contract: an unconditional restore frame can land between a field's focus and the next keystroke, so `n`/`c`/`m`/`/` no longer see an input target and the keystroke is consumed as a shortcut instead. The same unconditional pattern still exists in other overlays (`BoardAddMemberDialog`, `CardArchiveDialog`, `MarkdownEditor`, `CardModal`); those sites are not on the repaired paths and remain a known follow-up.
Routes: `/` (Home, see below; never redirects), `/profile` (account settings: display name, sign-in email, password, avatar upload, GitHub link), `/mcp-server` (session-authenticated MCP credential management), `/account-invites` (admin-only signup invite management), `/account-github` (admin-only instance GitHub App setup), `/all-workspaces` (admin-only: every workspace in the instance, each linking to `/w/<id>`; non-Admins are redirected to `/`), `/w/<id>` (one workspace's boards), its `/w/<id>/members` page (workspace members only) and `/w/<id>/settings` page (workspace admins only; others are redirected to `/w/<id>`), `/join-workspace/<id>` (accepts a workspace invitation), `/login`, `/signup`, `/board/:boardKey`. Every signed-in page renders inside the app shell (the sidebar and header: navigation links, avatar/email, sign out); everything but the auth pages sits behind the root route's session check. The public board route resolves the human board key to metadata via `GET /boards/by-key/:key`, mounting `BoardView` with the internal UUID.

Home (`/`, `HomePage`, [ADR 0066](../decisions/0066-workspace-model.md)): built on the client from the two existing lists, `GET /workspaces` and `GET /boards` (no dedicated endpoint). It renders one group per workspace the viewer is a member of (`access: "member"`), each titled with a link to `/w/<id>` and with its own "New board" button, whose dialog creates the board in that group's workspace (`POST /boards` always names `workspaceId`). Boards in a workspace the viewer is not a member of (`access: "guest"`, which `GET /boards` returns with `workspaceName`) sit together under one "Guest" heading, each row naming its workspace, with no New board button. Both lists carry only what the viewer holds as a member or Guest, an instance Admin included, so an Admin's Home has no other person's workspace or board (those are on `/all-workspaces`). With no member workspace and no guest board, Home shows "No workspaces yet."; the heading's "Create workspace" button is always there. Board rows are the shared `BoardRow` (name, key, Workspace/Restricted label); the per-board actions menu stays on a workspace's own board list.

- Same-column subtask families render inside their parent card, from one derived hierarchy: `BoardView` memoizes `buildSubtaskHierarchy` and owns session-only collapsed-family state (a family nobody closed is open, deleted ids are pruned, nothing is persisted or sent). `columnCards(state, columnId)` returns every card stored in a column — archive counts, the PR query set and column counters need that flat answer — while `columnRootCards` returns the draggable/rendered roots (a child nests only under a parent in the same column) the board and drag ordering use. A filter keeps a match reachable by rendering its active ancestor path and auto-expanding it at render time only (`renderedCollapsed`), so clearing a filter restores the reader's own expansion; a context ancestor is shown but not counted as a match. The sortable `<li>` is structural: a focusable body region owns dnd-kit's attributes, listeners and click-to-open, and the family footer/rows are siblings inside the same visual card, so a child control can never lift or open the parent. The drag preview retains the task body and progress footer, collapses family rows, and bounds its height, and `closeCard` resolves focus at frame time — the card's own control, then the nearest visible ancestor's disclosure or body, then the Search cards input.
