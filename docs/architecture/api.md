# API Worker (`apps/api`)

Part of [architecture](../architecture.md).

Hono on Cloudflare Workers. Exports the app type for the RPC client — `export type AppType = typeof app` — consumed by `hc` in `apps/web`; keep this export stable.

Auth: session cookie, sessions in D1. Configured account administrators (`ADMIN_EMAILS`: a comma-separated list of exact addresses, a `*@domain` entry is ignored because emails are not verified, [ADR 0071](../decisions/0071-admin-emails-exact-only.md)) act as global board operators for direct access: `requireMember` queries `boards` directly by id without creating `board_members` rows, bypassing membership for all guarded board, attachment, and WebSocket routes. Listing is not operator-wide: by default `GET /workspaces` and `GET /boards` return only what the viewer has as a member or a Guest (board owner or `board_members` row), an Admin included, and an Admin's guest workspace is tagged `access: "guest"`, never `"operator"`. An Admin gets every workspace only from `GET /workspaces/all` (`requireAdmin`: 403 for anyone else, 401 without a session; rows are tagged `member` or `operator` and count every board), and `GET /boards?workspaceId=<id>` lists every board of that workspace when the Admin is not a member of it (the Operator's workspace page); inside a workspace they belong to, they list as a member does. Ordinary users remain membership-scoped, and `requireMember` enforces the join (missing boards and unauthorized access both return 403). The app shell marks Operator access (an Admin who opens a workspace or board only through instance-Admin power: outside the workspace, or a member of it opening a Private board they were not added to) and Guest access next to the workspace name in the breadcrumb. `GET /boards/:id/members` returns only actual board members. Board metadata editing via `PATCH /boards/:id` (display name, unique uppercase key, validated icon and color) and permanent board deletion via `DELETE /boards/:id` are restricted to those who manage the board (the owner or an explicit board manager, each while still a member of its workspace, an admin of its workspace, or a configured account administrator); editing executes one atomic D1 UPDATE, maps unique board-key collisions narrowly to 409, and leaves BoardDO card storage and task numbers untouched.

Signup invites (`/invites`, Admin only) are single use and expire 7 days after they are made (`INVITE_TTL_MS`); `GET /invites` lists spent ones and unexpired unspent ones.

Account routes: `GET /me` (which also says whether the account has a password: `hasPassword`) and `PATCH /me` (display name, GitHub disconnect); `POST /auth/email` and `POST /auth/password` verify the current password first, behind the same per-IP rate limit as login/signup, and share login's per-account limit (`ACCOUNT_RATE_LIMITER`, 50 a minute keyed `account:<email>`, higher than the per-IP 10 so one IP cannot lock an owner out). An email change is refused when it would alter configured-admin status; a password change rotates the PBKDF2 hash compare-and-set and atomically deletes every other session row for the user. Login session insertion requires the verified password hash to remain current, so a login paused across rotation cannot create a new session from the old password. Linking GitHub uses the instance GitHub App's user sign-in (`GET /auth/github/start`, state cookie, then `GET /auth/github/callback`, which exchanges the code with the App's client id and secret from D1, ADR 0064) and stores the login name plus GitHub's numeric user id (`users.github_user_id`, unique, so one GitHub account links to one foxban account). The callback redirects to `/profile`, `/profile?github=error`, or `/profile?github=taken` when another account already has that GitHub account; `PATCH /me` with `githubLogin: null` disconnects and clears both columns.

Log in with GitHub ([ADR 0065](../decisions/0065-log-in-with-github.md)): `GET /auth/github/login/start` (public, `rateLimitAuth`) redirects to GitHub with the instance App's client id and a state kept in its own `github_login_state` cookie, and `GET /auth/github/login/callback` (public, `rateLimitAuth`) checks that state, exchanges the code with the same `fetchGitHubUser`, and looks the user up by `users.github_user_id` only, never by login name. A known id gets a normal session (`startSession`, so `POST /auth/password` revokes it like any other) and its stored `github_login` follows a GitHub rename; the redirect goes to `/`. Every other outcome redirects to `/login?github=error|cancelled|unlinked|exists|unavailable` (failed exchange or bad state, the person pressed Cancel on GitHub, no foxban account has that GitHub id and no invite let it sign up, a verified GitHub email already belongs to a foxban account, no GitHub App yet) and starts no session; the login page turns the reason into a message.

Sign up with GitHub (same ADR): the signup page's "Sign up with GitHub" link (shown only with an invite) is `/auth/github/login/start?invite=<token>`, which keeps the token in a `github_login_invite` cookie next to the state; the callback reads and clears it. A pending workspace invitation (the `#workspaceInvite=<workspaceId>.<token>` the login or signup page holds, which a full-page round trip would lose) rides the same way: the page's GitHub link adds `workspaceInvite=<workspaceId>.<token>` to the start URL, which keeps it in a short-lived httpOnly `github_login_workspace_invite` cookie only if it matches `^[\w-]{1,64}\.[\w-]{1,128}$`; the callback reads and clears the cookie, validates it again, and after a successful sign-in or sign-up redirects to `/join-workspace/<workspaceId>#invite=<token>` instead of `/`. A failed round trip goes back to `/login?github=...#workspaceInvite=...`, so a retry keeps it. A GitHub id no account has goes through `signUpWithGitHub`: it lists the GitHub account's verified emails (`GET /user/emails` with the user's token, which needs the App permission "Email addresses: read"; the token is not stored) and, if any equals an existing `users.email`, redirects to `?github=exists` ("sign in with your password, then link GitHub in Profile"), never linking by email. Otherwise it needs an invite: a missing, unknown or spent token is `?github=unlinked`, the same for all, and a valid one is spent in the same single D1 batch that inserts the user as email signup does (`createUserWithInvite`). The account keeps the primary verified email, or GitHub's `id+login@users.noreply.github.com` address when that email is on `ADMIN_EMAILS` or there is none, so GitHub signup never produces an Admin (Admin is derived from the email); if that no-reply address is on the admin list too (an entry naming that exact address), the signup is refused with `?github=error` and nothing is created or spent. `users.password_hash` is the marker `*` (`NO_PASSWORD_HASH`), which matches no password, so password login answers the normal generic 401. An account created this way can only sign in with GitHub until it sets a password: `POST /auth/password` without `currentPassword` does that, only while the marker is there, with the same compare-and-set and other-session revocation as a change (a second call needs the current password). Until then `PATCH /me` with `githubLogin: null` and `POST /auth/email` are refused with 403 `PASSWORD_REQUIRED` (the email refusal precedes any duplicate or admin check), so the account can never lock itself out; Profile shows "Set a password" for it.

Workspace roles (ADR 0066): a workspace has admins and members, and no owner. `workspace_members.role` is `admin` or `member`; `workspaces.owner_id` is only the creator, kept as a column and read for nothing. Admins manage settings, invites, members and every board in the workspace, Private ones included; any member may remove themselves, which is how a member leaves. A workspace always keeps at least one admin: demoting or removing the last one is refused with `409 last_admin` ("Promote another member to admin first."), checked by the route, again by the access-change evaluation and commit, and finally by the `workspace_keeps_an_admin_*` triggers from migration 0022, which raise inside the statement so two admins demoting each other at once leave one. Role changes, removals and leaving all run as `workspace-member-role` and `workspace-member-remove` access changes, so every board of the workspace has its cached access fenced and its open sockets dropped, Private boards included (their admins are what a role change moves). An invitation is only as good as the admin who issued it: it lists, inspects and accepts only while its `invited_by` is still an admin of the workspace, so demoting or removing an admin retires the invites they issued (promoting them again makes those work until they expire). Without this a demoted admin could leave and accept the admin invite they kept. The accept checks it in the route's read, again where the `workspace-invite-accept` attempt reserves the workspace (`authorityAssertions`), and again in `evaluateCommit` and in the commit's membership insert (`INVITER_IS_ADMIN`). A refusal answers `400 workspace_invite_unavailable`, the same as an expired or revoked invite and without saying why; a demotion that lands between the route's read and the reservation answers `409 access_change_conflict`, and a retry then gets the 400. An invite link is multi-use, so removing a member (not leaving) revokes every live invite of the workspace in the same commit batch: otherwise the removed member could accept the link they already used and rejoin ([ADR 0079](../decisions/0079-removal-revokes-workspace-invites.md)); the old links answer `400 workspace_invite_unavailable` and an admin issues new ones. An accept or an add that finds the membership already there answers success without an access change, so it fences and closes nothing; the cron deletes invites that expired or were revoked more than 30 days ago. Migration 0022 turned owner rows into admin rows. SQLite cannot alter the `role` CHECK, so `owner` is still an allowed value there, but a trigger rewrites any `owner` insert (the previous Worker's workspace creation) to `admin` in the same statement and nothing reads it; a later migration can drop the value once no such Worker can run.

Who may open a board (ADR 0066): an Operator, the board's owner, a board member (any `board_members` row, so a Guest too), a member of its workspace while it is a Workspace board (`access_mode='workspace'`), or an admin of its workspace whatever its mode. A Private board (`access_mode='restricted'`) is therefore closed to a workspace member who was not added, and open to the workspace's admins, who also manage it (rename, move, delete, members, columns) with no `board_members` row. The rule has one copy in `apps/api/src/auth.ts`: `boardOpenSql` / `boardManageSql` build it as SQL (board alias, viewer expression, and an operator term each site chooses: default lists leave it out, `GET /boards?workspaceId=` counts an Admin outside the workspace, `transfer-options` never has it), and `canOpenBoard` / `canManageBoard` decide it in TS from already-read rows (`toBoardRow`, the BoardDO's `currentBoardAccess`, and `evaluateCommit` in `access-changes.ts`). Every surface uses them: `findAccessibleBoardWhere` (behind `requireMember` and `GET /boards/by-key/:key`, so REST routes and the WebSocket connect), the `GET /boards` list, the BoardDO re-check, the member and candidate reads, the `PATCH /boards/:id` write predicate, `transfer-options`, the workspace board counts, the MCP `get_board` member read, and the recipient visibility and board predicates in `access-changes.ts`. A new surface uses the builder and adds a row in `apps/api/test/workspace-admin-private-boards.test.ts`. Effective board membership (`boardMemberSql`, used by `currentAssigneeEligible`, the member lists and transfer assignee preservation) is deliberately narrower: it follows board members and Workspace-board members, so an admin who wants to be assigned work on a Private board is added to it. Manage rights (`canManageBoard` / `boardManageSql`) differ from open rights in one term: the board's creator and an explicit board manager manage only while they are still a member of the board's workspace, so one who was removed or who left keeps the open right (their grant and ownership stay) but cannot delete, move, rename or change the columns of the board. A board manager (`board_members.role='manager'`, granted to the mover by a board move) is removed only by someone who manages the board: the route answers `403`, and the reservation and the commit assert it again. Moving a board into the workspace it is already in answers `400 board is already in that workspace` before any access change starts. Board metadata carries `viaWorkspaceAdmin`, true for an admin who opens a Private board only through the workspace (not its owner, not a board member); the board page shows a note for it and it grants nothing.

Deleting a workspace (ADR 0066): `DELETE /workspaces/:id` is for a workspace admin only. A member, a Guest, a stranger and an Operator who is not a member of it get `403` (an instance Admin who is also an admin of the workspace deletes it like anyone). It is one D1 batch, so one transaction: it reads the member ids, then runs a single `DELETE FROM workspaces` that carries the caller's admin row, "no row in `boards` for this workspace" (every board, including a Private one the admin cannot open) and "no `access_change_scopes` row for it", and only then deletes the workspace's members and invites, each guarded by the workspace row being gone (so a refusal leaves them alone and the last-admin triggers, which stand down once the row is gone, never see the member delete). A refusal is `409 workspace_not_empty` ("Move or delete this workspace's boards first.") or `409 access_change_conflict` (a journaled access change holds the workspace, which includes a board move into or out of it). Because the emptiness check and the delete are one statement, a board created or moved in at the same moment either lands first and is seen, or finds no workspace: `POST /boards` inserts only while the creator's membership row exists, a board move reserves its destination's scope and asserts the mover's membership there, and the `boards_workspace_valid_insert` and `boards_workspace_required_update` triggers from migration 0012 refuse any board placed in a workspace that does not exist. No migration is needed. Former members with an open presence socket get a `workspace.invalidated` hint, best effort (the same `sendPresenceInvalidate` that access changes use to notify, in bounded batches); anyone else sees the workspace go when their lists next refresh.

The access-change journal keeps a settled operation for 30 days: the cron pass deletes `access_change_operations` rows that are `completed` and `notified` and older than that, with their `access_change_boards` rows, in batches of 500. Within the window an attempt id replays its recorded answer; after it the id is a new attempt, which the current state either repeats idempotently or refuses. The pass finds unfinished rows by phase (`preparing`, `committed`, `aborted`, or `completed` and not yet notified), so the `(phase, notified, updated_at)` index serves it.

Board membership routes are guarded by `requireMember`. Candidate discovery ([ADR 0072](../decisions/0072-member-picker-workspace-scope.md)) returns the members of the board's workspace who hold no `board_members` row, never the whole instance; `GET /boards/:id/membership-candidates?email=<address>` instead returns at most the one account with exactly that address (so an outside Guest is added by typing a full email, and a partial address finds nothing). `GET /workspaces/:id/membership-candidates?email=<address>`, for the workspace's admins, answers the same way for adding an existing account to a workspace directly: at most the one account with exactly that address who holds no membership there, and an empty list without an address (the instance's accounts are never listed). Both exact-email lookups are limited to 10 a minute per signed-in user (`rateLimitLookup`, the `AUTH_RATE_LIMITER` binding keyed `lookup:<userId>`, skipped like `rateLimitAuth` when the binding or a non-loopback `CF-Connecting-IP` is absent) and answer `429` past it. Anyone who can open the board may add or list; additions and removals use stable user ids. `DELETE /boards/:id/members/:userId` is idempotent for absent rows but rejects the board owner and the caller themselves. Deleting a membership row runs as a `board-member-remove` access change: it revokes subsequent guarded REST requests and WebSocket handshakes, and the fence closes the board's open sockets (close code 4010) so the removed person's connection does not outlive it.

Column structure is a separate owner/admin boundary: only the owner of that particular board (while still a member of its workspace) or an existing account administrator may create, rename, reorder or delete its columns. Owning another board grants no column rights here. Ordinary members retain card collaboration, membership management and label operations; board creation and the existing owner/admin rules for board metadata and deletion are unchanged. See [ADR 0050](../decisions/0050-owner-admin-column-management.md).

Cross-board card transfer routes: `GET /boards/:id/transfer-options` returns accessible destination boards (`id`, `name`, `key`; no columns, so listing wakes no board), by the member, Guest and workspace-admin rule for everyone: an instance Admin may open the source as an Operator but is not offered every board in the instance. A board mid access change is left out of the list. `GET /boards/:id/transfer-options/:destinationBoardId` returns that one destination's live `{ columns }` from its BoardDO under the same access rule (`403` otherwise, `503` with `Retry-After` when the board cannot answer); the transfer dialog calls it when a destination is selected. `POST /boards/:id/cards/:cardId/transfer` executes an idempotent saga:
- Source preparation: validates that the card has no cross-card relations/links (rejecting with HTTP 409 if present), records operation in `card_transfer_operations` (state `'prepared'`, monotonically increasing generation per card), creates a non-expiring write fence in `card_transfer_locks`, and exports the bundle. Reusing an already terminated (finalized or aborted) `transferId` is rejected with HTTP 409 Conflict. The source write fence remains active until terminal state (`finalized` or `aborted`) is reached; it does not expire via TTL.
- Markdown URL rewriting: card descriptions and comments have their attachment URLs rewritten from `/boards/:sourceBoardId/attachments/:id` to `/boards/:destinationBoardId/attachments/:id` via `rewriteAttachmentUrls` in `@foxban/shared`, using exact AST parser token offsets (`resourceDestinationString`, `definitionDestinationString`) to preserve code spans, brackets, entity encodings, and angle brackets.
- R2 copy & staging leases: attachment files are copied to transfer-scoped destination R2 paths (`${destinationBoardId}/${transferId}/${attachmentId}`), with destination staging leases registered in `attachment_cleanup`.
- Destination import: destination BoardDO checks for an existing receipt. If an abort tombstone exists (`taskNumber = -1`), import is rejected with 409. It performs pre-write lease validation inside the transaction, verifying active staging leases in `attachment_cleanup` (`delete_after > now AND claim_token IS NULL AND deleted_at IS NULL`) for all bundle attachments before executing any database writes or allocating destination task numbers; expired, claimed, or tombstoned staging leases throw `ImportConflictError(409)` triggering transactional rollback without partial commits. Transfer U import consumes only U's staging row (`destObjectKey`), while aborted transfer T's staging rows remain untouched in `attachment_cleanup` until collectible. On success, allocates a monotonic destination task number and fractional position, and persists receipt in `card_transfer_receipts` (keyed by `transfer_id`).
- Two-phase finalization & terminal destination fencing: source deletion occurs only after destination commit. In compensation handlers and lock release, destination abort (`CARD_TRANSFER_ABORT_PATH`) is established first. If destination committed, source finalizes the exact current generation (cascading card aggregate and marking operation `'finalized'`); if destination aborted, destination records an abort tombstone (`taskNumber = -1`), source releases the lock, and operation marks `'aborted'`. If destination is unreachable, the source write fence is retained. Worker compensation performs no foreground R2 deletion; uncommitted transfer-scoped staging blobs are safely collected by the destination BoardDO TTL durable collector / alarm sweep, where successful deletion stamps a permanent tombstone (`deleted_at`).
- One coordinator: `apps/api/src/card-transfer.ts` owns the step order, compensation, receipt lookup and status-to-outcome mapping. `run` serves this route; `settle` serves the BoardDO alarm, the access-change fence, a stale-lock takeover in prepare and the release endpoint. It reaches the boards through `SourceParticipant` / `DestinationParticipant`: thin wrappers over the `BoardClient` (`boardSource`, `boardDestination`; see [BoardDO](board-do.md)), the DO's local source (`localTransferSource`), and fakes in `test/card-transfer.test.ts`.
- Frontend transfer operation ID semantics: `TransferCardDialog` manages the client-side `transferId`. When submitting a transfer, the operation ID is preserved across ambiguous network failures or 500 server errors so retries remain idempotent and resume the in-flight saga. A terminal conflict instead rotates the dialog to a fresh UUID (`transferId`) and clears the destination binding, because the supplied operation can never commit. Terminality is decided by `isTerminalTransferConflict(status, data)` in this order:
  - `code === TRANSFER_TERMINAL_CODE` (`"transfer_terminal"`, exported from `@foxban/shared`) — the stable primary discriminator. Every terminal transfer rejection the Worker and BoardDO emit (terminated/reused operation id, card or destination identity mismatch, generation mismatch, abort tombstone, lock mismatch, destination identity unknown) carries this code alongside its HTTP status, and the Worker forwards the code when relaying a DO 409, so prose is never load-bearing.
  - HTTP 410, or `aborted: true` in the body.
  - An uncoded 409 is non-terminal regardless of its prose — the operation is still live server-side — so the dialog preserves the operation id and shows no new-operation notice. Human error text is display-only.

  Changing the destination board or column also rotates the id, so a resubmission never collides with a receipt or generation lock bound to the previous destination.

The Workers runtime is NOT Node: no `fs`, no `net`, no Node-only npm packages. Check compatibility before adding dependencies.

Attachment bytes live in the membership-gated `ATTACHMENTS` R2 bucket under `boardId/uuid` (for ordinary attachments) or `${destinationBoardId}/${transferId}/${attachmentId}` (for transferred attachments, where `transferId` is a safe 1–64-character Identifier and `attachmentId` is a UUID); the upload route canonicalizes the declared MIME type, registers a one-hour provisional lease in that board's DO, writes R2, and returns the authoritative type/size for `attachment.create` to claim. The serve route asks the board's DO for the object's key; a genuine "no row" answer falls back to `boardId/uuid`, but a board that cannot answer gets 503 with `Retry-After` instead, since guessing would 404 a transferred object. Exact PNG/JPEG/GIF/WebP metadata is served inline; every other stored or missing type is forced to `application/octet-stream` with `Content-Disposition: attachment` and `nosniff`. Explicit attachment deletion enqueues its R2 key through a DO SQLite trigger, then the shared alarm deletes the object, records a permanent terminal tombstone (setting `deleted_at` and `reason = 'deleted'`), and reschedules after failures. Individual card deletion and populated column deletion instead archive cards and preserve their attachment metadata and blobs until retention expiry. Ordinary attachment publication (`attachment.create`) transactionally validates that an exact matching cleanup lease by `object_key` exists in `attachment_cleanup`, is in `'staged'` state, is unexpired (`delete_after > now`), and is unclaimed and not tombstoned (`claim_token IS NULL AND deleted_at IS NULL`) before inserting metadata; missing, expired, claimed, or tombstoned leases reject the transaction before any write. The DO distinguishes an **idle tombstone state** (`deleted_at IS NOT NULL`, `reason = 'deleted'`, retained `claim_token`, `delete_after = 0`) from an **explicit redelete tombstone state** (`delete_after = now` or bounded retry `delete_after = retryAt`). Idle tombstones are excluded from alarm queries and due work (`WHERE deleted_at IS NULL OR (deleted_at IS NOT NULL AND delete_after > 0)`), preventing alarm loops. When global reconciliation (`reconcileAttachmentObjects` via `RECONCILE_ATTACHMENTS_PATH`) observes an exact unowned R2 object key matching an existing tombstone—such as an authorized pre-delete PUT that completed late after lease expiration or tombstoning—it transitions the row to the due redelete state (`delete_after = now`, `reason = 'deleted'`) and triggers alarm drain to re-delete the object bytes. Successful R2 deletion returns the row to the idle tombstone state (`delete_after = 0`, alarm null); deletion failure retains the claim fence and reschedules with a bounded retry delay (`delete_after = retryAt`, where `retryAt = now + 60_000`), scheduling the alarm at `retryAt`. Throughout both idle and redelete/retry states, the publication and staging fence is continuously maintained (`deleted_at IS NOT NULL`, `claim_token IS NOT NULL`, `reason = 'deleted'`); staging (`STAGE_ATTACHMENT_PATH`), import (`CARD_TRANSFER_IMPORT_PATH`), and ordinary publication (`attachment.create`) reject any tombstoned key with HTTP 409 Conflict. Fresh uploads and transfers generate fresh non-reusable keys (with UUID attachment IDs and safe 1–64-character Identifier transfer IDs). Tombstones persist for the lifetime of the board DO; deleting a board via `/internal/board/delete` purges the R2 key prefix and board-content rows, retaining a durable deleted marker and transfer outcomes for recovery (ADR 0061). Attachment reconciliation remains available to collect writes that finish after deletion.

## Authenticated MCP (`apps/api`)

`/mcp` is a stateless Streamable HTTP endpoint served by the existing Worker. Bearer credentials are independent of browser sessions and carry an explicit current user, stable board-id allowlist, closed scopes (`boards:read`, `tasks:write`, `comments:write`), expiry and revocation state. D1 stores only the SHA-256 token digest and management metadata. Every tool callback reloads the credential, user, scope and current board authorization; admin access never widens the credential.

Signed-in users manage their own credentials at `/mcp-server`. The page lists metadata through cursor pagination and issues or revokes credentials through the session-only `/me/agent-credentials` routes. A raw token exists only in page-local reveal state after the successful POST response: it never enters TanStack Query, browser storage, URLs or browser-test artifacts. During that reveal the user may copy the token alone, a generic `mcpServers` JSON configuration, or a VS Code `servers` JSON configuration; both configuration payloads are built only for the clipboard and embed the current-origin endpoint plus bearer token. An ambiguous response warns the user to inspect and revoke metadata rather than retrying issuance automatically.

Thirteen strict tools expose bounded board/task reads, task creation, title/description update, task move, linked-subtask completion/reopening (a move to the completed or starting column), top-level comment creation, and ordinary label definition/assignment management. Board and task reads page label definitions and exact card-label join IDs; `status:*` remains only a naming convention. The strict `get_board` column output carries `starting` and `completed` booleans; both are false on every column of a board with fewer than two columns. Board content remains exclusively in BoardDO SQLite. Internal typed POST routes perform bounded reads or the nine narrow commands; callers cannot submit arbitrary WebSocket messages or trusted headers. MCP and browser mutations share domain guards, transactional apply/activity behavior and ordered WebSocket fan-out.

Each mutation carries a caller UUID `operationKey`. BoardDO schema v23 stores a receipt keyed by credential and operation key, bound to actor, operation and canonical input hash in the same transaction as the mutation and committed result. Exact retries return the historical result without applying or broadcasting again. The board's lifecycle alarm deletes receipts older than 30 days when it runs (a receipt never schedules an alarm), after which a retry of that key is a new operation; authorization is rechecked before receipt lookup.
