# GitHub integration (`apps/api`)

Part of [architecture](../architecture.md).

Instance GitHub App ([ADR 0064](../decisions/0064-instance-github-app-webhook-development-info.md)): an Admin creates the instance's one GitHub App through GitHub's app-manifest flow. `GET /github-app` (status: the App's public fields and an install link, plus `canCreate`) and `POST /github-app/manifest` (the manifest, built from `appOrigin`, and the GitHub form target carrying a CSRF `state` cookie) are Admin-only; `GET /auth/github-app/manifest/callback` checks the state cookie, converts GitHub's `code` (`POST /app-manifests/{code}/conversions`) and writes the single `github_app` row, then redirects to `/account-github?githubApp=created|error`. The private key, webhook secret and client secret are AES-GCM sealed (WebCrypto, column name as AAD) with the `GITHUB_APP_ENCRYPTION_KEY` Worker secret (base64 of 32 bytes), which `scripts/deploy.mjs` generates only when the Worker has none; `canCreate` and the manifest route check the key actually imports, so a malformed key refuses with 503 before GitHub spends its one-time code; no response ever carries them, and the existing App is never replaced. The webhook URL in the manifest is `/webhooks/github`. This is the only GitHub App foxban uses: the per-board repository connection of ADR 0041 (the `boards.github_*` columns, `github_connection_states`, the connect, setup and callback routes and the env-configured App) was removed by migration 0020, so an upgraded instance starts with no App until an Admin presses the button.

Webhooks and connected repos (ADR 0064): `POST /webhooks/github` is public and authenticated by signature alone. It reads the raw body (413 when it is over 5 MB, by `Content-Length` before reading or by the bytes read; GitHub does not redeliver a 413, so a push that large leaves its branch tip until the next event or backfill), checks `X-Hub-Signature-256` (HMAC-SHA256 with the decrypted webhook secret, constant-time) and only then parses; no App is 404, a bad or missing signature 401, an unparsable signed body 400. Every other outcome is 2xx, because GitHub does not retry failed deliveries, except a failure that is the delivery's own: a GitHub error (502, such as confirming an installation's owner or re-reading a branch) or a board-write error (500), which GitHub shows in its delivery log. Since GitHub will not retry it, a failed `pull_request`, `push`, `create` or `delete` event for a connected repo queues that repo for backfill (`repairLater`: the raw `repository.id`, only when it is a safe positive integer and the repo is connected; a queue failure never hides the original error), so the minute cron re-reads the repo and repairs the card's development info. The App is public, so anyone can install it: `installation` and `installation_repositories` events add repos to `github_repos` (repo id, installation id, `full_name`, private flag) only when `installation.account.login` equals the App owner's login from `GET /app` (App JWT, case-insensitive); an `installation_repositories` "added" also mints an installation token scoped to the added repo ids, and on a 404 or 422 (the repo was removed since, the deliveries arrived out of order) re-reads the install instead of connecting (ADR 0088); removals (`installation` deleted/suspend, `repositories_removed`) need no check, since only owned installations were ever connected. `pull_request`, `push`, `create` and `delete` events return `dropped` unless `repository.id` is a connected repo. A connected repo's `pull_request`, `push`, `create` and `delete` events become development info (below), `applied` when a card changed and `dropped` otherwise. `GET /github-app` (the Admin page) first re-reads the owner's active installations (`GET /app/installations`, an installation token, `GET /installation/repositories`, up to 10 and 50 pages of 100) and makes `github_repos` match, so missed events heal; when either list hit its page cap it may be partial, so repos are still added but none is dropped (ADR 0088); if GitHub cannot be asked it returns the last known repos with `reposRefreshed: false`. It also returns the App `owner`, the `ignoredAccounts` whose installs it skipped, and `settingsUrl` (the App's Advanced settings, where ownership is transferred), so the page can say why an install on another account connects nothing. `DELETE /github-app` (Admin) forgets the App so another can be created: it drops the `github_app` row, `github_repos` and the backfill queue in one batch, and keeps card development info and the PR and branch routes, whose ids are GitHub's and still match a new App on the same repos. GitHub keeps the App until its owner deletes it there. The private key GitHub returns is PKCS#1 and is wrapped into PKCS#8 in `github.ts` before WebCrypto signs the App JWT.

Development info from pull requests (ADR 0064): `github-development.ts` turns a connected repo's `pull_request` event into a write to each board that holds it. `task-keys.ts` reads task keys from the head branch, title and body: a board key (2 to 10 letters or digits, starting with a letter), a hyphen and a task number with no leading zero, not touching other letters or digits, case-insensitive, at most 20 distinct keys per event. `kr-42-fix` and `fix/KR-42_x` name KR-42; `KR-420`, `KR-42x` and `XKR-42` do not. Keys resolve to boards through `boards.board_key` (unknown keys fall away), and only when the PR's head is in the connected repo itself (`head.repo.id` equals `repository.id`, [ADR 0088](../decisions/0088-fork-prs-not-key-linked-and-bounded-github-reads.md)): a fork's PR, or one whose head repo is gone, names stranger-written text and links nothing by key, though a manual link or an existing route keeps it updating; boards also come from the D1 routing table `github_pr_routes(repo_id, pr_number, board_id)`, so a linked PR keeps updating after its text stops naming the key. The routing table is pointers only, no card data; the BoardDO writes it through `github-pr-routes.ts` (`syncPullRequestRoute`) after each webhook write, on a transfer and when cards are deleted, and reads join `boards` so a deleted board's pointer is ignored. Links follow the card: a board-key edit, archive and restore, or a title that stops naming the key leave them in place (existing links update whatever the text says), a transfer carries them in the bundle (`developmentPullRequests`) and points the routing table at the destination board before the import commits, and a purge deletes the rows and drops the board's pointer unless another card on the board still holds the PR. A pointer is a hint that heals itself: a stale one is dropped by the next event for its PR, so only the add before a transfer commits is awaited, and the drops run after the card is gone. Each board receives `POST /internal/github/pull-request` with the PR (`repositoryId`, `repository`, `number`, `title`, `state` of open, draft, merged or closed (`pullRequestState` in `github.ts`, the one mapping for webhook events, REST reads and the create-pull-request answer), `url`, `updatedAt`) and the task numbers its text named for that board's key; it links those active cards on first sight and updates every card that already links the PR. A row is written unless the stored `updated_at` (epoch ms, GitHub's own second-resolution clock) is later than the event's. An equal one still writes, because a follow-up in the same second as the stored event must win, while a write that would change nothing is skipped and not announced; so late deliveries cannot roll state back and a replay is idempotent and silent. Members read `GET /boards/:id/cards/:cardId/development` (`{ pullRequests, branches }`, newest update or commit first, no GitHub call; 404 for a missing or archived card). `push`, `create` and `delete` payloads carry no usable "last updated" field (`create` and `delete` have none; `push` has only committer-supplied commit timestamps), which is why branch events re-read the branch instead of trusting payload order.

Development info from branches (ADR 0064): `github-branches.ts` handles `push` (a `refs/heads/` ref; tags are ignored), `create` and `delete` (`ref_type: "branch"`). The branch name is read for task keys like a PR's text; a name that holds no key of a known board costs no GitHub call. Otherwise the Worker mints an installation token for the repo's installation (`github_repos.installation_id`) and re-reads the branch (`GET /repos/{repo}/branches/{name}`): the tip's sha, first message line, committer time and the branch's web URL, or a 404. Whatever the event said, the card shows that answer, so a `delete` for a branch that exists again changes nothing and a `push` for a branch that is gone removes it. A branch's boards come from the keys in its name and from the D1 routing table `github_branch_routes(repo_id, branch_name, board_id)` (migration 0021; pointers only, no card data), so a linked branch keeps updating, and a `delete` still applies, after its board's key is edited or its card moved to another board. A routed board with no key match is told with no task numbers, so it updates only cards that already link the branch. The BoardDO keeps the table current through `github-branch-routes.ts` (`syncBranchRoute`), like the PR table: after each branch write and unlink, before a transfer import commits (and again after it), and when cards are purged or leave in a transfer; reads join `boards`, so a deleted board's pointer is ignored. Branch links follow the card like PR links: the transfer bundle carries the branch rows (`developmentBranches`, each with its `observedAt`, so the read that ordered a row still orders it) next to `developmentPullRequests`. Members unlink a branch with `DELETE /boards/:id/cards/:cardId/development/branches/:repositoryId/:name` (the name URL-encoded, since it may hold slashes): it removes the row, records a `branch` tombstone in `card_development_unlinks` so key matching never links that branch to that card again, updates the pointer, announces the card and answers with the card's development info (404 `not_linked` when the card did not link it). A branch cannot be linked by hand. Each board receives `POST /internal/github/branch` with `{repositoryId, repository, name, head | null, observedAt, taskNumbers}`; `observedAt` is when the re-read began and orders writes (a write is skipped when the stored row came from a later read), and cards are announced only when the shown commit changed. Branch rows keep one latest commit, never history. A removal by a delete event leaves no marker, so a read that began before a delete but is applied after it can briefly bring a branch back; the next event for that name corrects it. The GitHub calls (an installation token and one read) run inside the webhook request, well inside the 10 seconds GitHub allows.

Backfill on connect (ADR 0064): `github-backfill.ts` fills cards with a repo's existing work when it is connected. A repo added by an owned `installation` or `installation_repositories` event is queued in D1 `github_backfill_queue(repo_id, queued_at, run_after, attempts)`; the webhook then runs `drainBackfill` in `ctx.waitUntil` (after the 2xx, so the 10-second delivery limit does not bind) and the every-minute cron drains whatever is due, so the job is queue-less and survives any single invocation. The Admin page's re-read (`refreshConnectedRepos`) queues the repos it newly connects the same way, for a repo whose `installation` webhook never arrived; the cron drains them. A drain claims one due repo at a time under a lease (`run_after` pushed 2 minutes out) and stops claiming after 20 s or about 300 subrequests. The claim counts as an attempt (`attempts` is incremented in the claim's own UPDATE), so a repo whose failure handling cannot run, for instance a run killed by the time limit or a hung fetch, still reaches the drop at 5: the claim deletes a due row that already has 5 attempts instead of claiming it again. Subrequests are counted as they are spent: a PR costs 2 D1 reads plus one board call per matched board, a branch one read plus one call per named board, each list page one. A repo that would pass 900 stops cleanly before the next step and ends the drain; it stays queued with the attempt counted and is held like any other failure (5 minutes times the attempt count), so the rest of the queue gets its turns, and one too big to ever fit is dropped after 5 attempts with a warning. Per repo it lists open PRs (all pages, no window), closed PRs (`state=closed&sort=updated&direction=desc`, GitHub has no `since`, so it stops at the first PR whose `updated_at` is older than 30 days and keeps only those whose `closed_at` is inside the window) and all branch names (100 per page; PR lists use 30 per page, since 100 full PR objects pass the 2 MiB response cap), then sends PRs (a fork's PR counts as naming no key) and branches that name a task key, or that already have a route in `github_pr_routes` or `github_branch_routes` (a hand-linked PR, a branch whose card moved board; each table read once per repo), through `handlePullRequestEvent` and `writeBranch`, the same matcher and board writes webhooks use (a branch costs one `GET /branches/{name}`; the other branches cost none). Writes are idempotent (newer `updated_at` and later `observedAt` win, unchanged rows are not announced), so a rerun, a retry after a partial run, or a re-add changes nothing. A rate-limited call (429, or 403 with `Retry-After` or no quota left) holds the repo until `Retry-After` has passed and ends the drain; a rate limit does not count as an attempt; any other failure retries after 5 minutes times the attempt count and is dropped after 5 attempts. Limits: at most 34 pages per PR list (about 1000 PRs) and 30 pages of branch names and 100 key-naming PRs and 100 key-naming branches per repo (the oldest fall off; a resumable cursor would lift this), and it assumes the Workers Paid subrequest limit.

Write-back (ADR 0064): `POST /boards/:id/cards/:cardId/development/create-branch` and `.../create-pull-request`, each with `{ repositoryId }` naming one of the instance's connected repos (`GET /boards/:id/connected-repos`, D1 only), act through the instance App's installation token, so the author is `foxban[bot]` and the pull request body says "Opened by <name>". The branch is named from the task key; neither route links anything itself, the `create` and `pull_request` webhooks bring the result back onto the card like any other. Without an App they answer 503. Manual links: `POST /boards/:id/cards/:cardId/development/pull-requests` (`{ pullRequest: number | URL, repositoryId? }`, validated against GitHub, stored as a link with no key match) and `DELETE .../development/pull-requests/:repositoryId/:number` (records the tombstone key matching honours). Both write routes revalidate current board access, access-change state, the repo's installation and active card identity after preparatory GitHub reads and immediately before the external write. These checks reject changes completed during those reads; D1 authorization and a GitHub write cannot form one atomic transaction.
