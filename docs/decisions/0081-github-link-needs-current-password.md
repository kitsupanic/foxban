# 0081 — Linking GitHub needs the current password

## Status
Accepted — 2026-11-19; amends 0065 (its "first password on the session alone").

## Context
Since 0065 a linked GitHub id (`users.github_user_id`) signs in like a password does. Linking was still a plain navigation, `GET /auth/github/start` then `GET /auth/github/callback`, that asked only for a session. Two holes followed. Someone holding a stolen session cookie, without the password, linked their own GitHub account; when the owner then changed the password (which signs the other sessions out), the thief signed back in with GitHub. And the callback wrote the id unconditionally, so for a GitHub-only account it replaced the owner's id and locked the owner out of GitHub login. The OAuth `state` is a double-submit cookie, which any browser can set for itself, so it proves nothing about who started the flow.

Closing those two left a chain for a GitHub-only account, one with no password (`password_hash` is the `*` marker), whose owner signed in with GitHub. A thief holding only its session: (1) sets a first password, which 0065 allowed on the session alone and which also signs the owner's other sessions out; (2) disconnects GitHub with `PATCH /me { githubLogin: null }`, which needs only that a password now exists; (3) links their own GitHub account, giving the current password they just set. The owner is locked out and the thief holds both credentials. The root is step 1: a first password is a new sign-in credential, and the session was the only proof asked for it.

## Decision
- A link starts with `POST /auth/github/link` (session, per-IP and per-account limits like the password routes, body `{ currentPassword? }`). An account with a password must send it: a missing or wrong one is the generic `401 invalid credentials`, and nothing is stored. An account with no password sends none. The answer is `{ url }`, the GitHub authorize URL, and the browser goes there with `window.location.assign`.
- The start stores a SHA-256 of the new `state`, an expiry ten minutes out and the flow's purpose (`'link'` or `'reauth'`) on the caller's `sessions` row (migration 0025: `github_link_state_hash`, `github_link_expires_at`, `github_link_purpose`), next to the state cookie. The callback needs the cookie to equal the query and the stored hash to equal the hash of the query state before it expires. It clears the stored state first, in the same batch, so a state is good for one callback whether that callback succeeds or not. A password change that deletes a session deletes its pending state too.
- `GET /auth/github/start` is gone.
- The callback's link write is `WHERE github_user_id IS NULL OR github_user_id = <the account that approved>`. It fills an empty slot or follows a rename of the same GitHub account, and never replaces a different id: that needs a disconnect first, and a disconnect needs only that the account has a password (0065), so it is refused for one with none. A refused write redirects to `/profile?github=error`. The unique index still maps a GitHub account another foxban account holds to `?github=taken`.
- Setting a first password, on an account with no password, needs a fresh GitHub approval in the same session, by the account's own GitHub id. `POST /auth/github/reauth` (session, per-IP and per-account limits; `400` for an account that already has a password; `503` without a GitHub App) starts the same round trip as a link, with purpose `'reauth'`, and answers `{ url }`. Its callback is the existing `/auth/github/callback`, not a new URL: GitHub matches callback URLs exactly, and an App created before this change keeps the list it was created with, so a new path would fail until an Admin recreated the App. The stored purpose picks what the one callback does, so a `'reauth'` state never links and a `'link'` state never confirms.
- The reauth callback runs the same checks as a link (cookie, stored hash, expiry, single use) and the same code exchange. It writes `sessions.github_reauth_until`, ten minutes out, only when the approving account's numeric id equals the user's stored `github_user_id`; with no stored id there is nothing to match and it never writes. It links and renames nothing. It redirects to `/profile?github=reauthed`, or `/profile?github=reauth-error` when it wrote nothing.
- `POST /auth/password` for an account with no password needs that proof on the calling session, still in the future: else `401 { error: "confirm with GitHub first", code: "GITHUB_REAUTH_REQUIRED" }`, nothing changed and no session revoked. The proof is checked again inside the batch that sets the password and cleared by it, so it is spent once and cannot lapse between the check and the write. The rest of the handler is as in 0065: compare-and-set against the marker, every other session deleted in the same batch, their sockets closed (0082).
- Profile's "Connect GitHub" is a button. For an account with a password it opens a dialog for the current password; for one without it starts the link at once. "Set a password" for an account with none goes to GitHub first through `POST /auth/github/reauth`, and opens its form when GitHub sends the browser back with `?github=reauthed`; a `401` on the save sends the person back to that GitHub step.

## Consequences
A stolen session can no longer add a GitHub sign-in method on its own, which closes the path where a thief's own GitHub login survived the owner's password change. This does not make a password change end a thief's access in every case; what remains is listed below. The chain above stops at step 1: the thief is not signed in to the owner's GitHub account, so the id check fails, no password is set, no session is revoked, and the disconnect stays refused. An account with no password can still link into an empty GitHub slot (it has nothing to prove); an account with an id cannot be moved to another one, it can only approve the same account again. GitHub may skip its consent page for an App the person already authorized, so the proof is the id of the GitHub account signed in in that browser, not a click. An account with no password and no stored GitHub id has no sign-in credential at all; it cannot set a first password until GitHub is linked (the empty slot fills, then the reauth matches). What remains, stated plainly:
- MCP agent credentials (`POST /me/agent-credentials`, valid up to 90 days) are issued on the session alone and survive a password change (`docs/mcp.md`, unchanged here). Known follow-up, not fixed here.
- The session the owner changes the password from keeps working (0026). A thief holding that very session is not signed out.
- `PATCH /me` can disconnect GitHub on the session alone when a password exists, which can lock out an owner who forgot the password (pre-existing). Known follow-up, not fixed here.
- An account with no password cannot add one while the instance GitHub App is removed (`503` on the reauth start) or the user's GitHub account is gone (the approval cannot match), and such an account is locked out once its session expires.

Rejected: using the state cookie as proof of the password check (an attacker sets their own cookie); a short-lived signed token handed to the browser (the stored hash needs no new secret and dies with the session); asking for the password at the callback (the browser has just left the app, and the password would travel in a navigation); a separate reauth callback URL (breaks Apps already created, see above); keeping the first password on the session alone (the chain above).
