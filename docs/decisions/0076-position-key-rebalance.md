# 0076 — Long position keys are rebalanced by the board

## Status
Accepted — 2026-11-19; amends 0006 ("a move writes one row") and 0010 ("no rebalancing pass").

## Context
Clients compute position keys against their own sorted state (ADR 0010). Dropping again and again into the same gap grows the key by about a character every six drops, so after 373 drops the key passes the wire's 64-character `Position` bound. From then on every `card.move` and `card.create` into that gap fails schema validation, and the MCP placement refuses with `position_conflict`. Nothing ever shortened a key.

## Decision
- `runMutation` (`board-mutations.ts`) checks the keys a mutation wrote: `card.create`, `card.move`, `card.restore`, `card.finish`, `column.create`, `column.move`. If any is longer than `REBALANCE_KEY_LENGTH` (40), then in the same transaction every active card of that column (or every column of the board) gets a fresh key from `generateNKeysBetween(null, null, n)`, assigned in the order they already have (`position`, then `id`, the same order every client sorts by). Archived cards keep their keys; a restore brings its own. Other columns are untouched.
- The outcome carries the rewritten `{ id, position }` list (null when nothing was rewritten). The BoardDO sends it as a `positions.rebalanced` frame (`table: "cards" | "columns"`, `positions`) to every socket, sender included, after the mutation's other frames, on the socket and the MCP path alike. The mutation frame itself is still relayed verbatim (ADR 0010), carrying the key the client chose. The new frame is not in older clients' schema, so the realtime protocol version moves to 12 (ADR 0045).
- The frame is a peer change, not a snapshot. A client sets the listed keys on its authoritative base and rebases its pending optimistic mutations over it, exactly as for any peer frame. A snapshot would be wrong here: a client treats a snapshot as a reconnect, clears its pending mutations and reports the ones it does not find as unverified, but on a live socket "not in it yet" only means "not processed yet".
- Accepted race: a pending move carries a key computed against the old neighbours, so after the rebase it sorts wherever that key now falls, which can be one slot off, and a peer's move computed the same way can land that way on the server. A key that is long again can trigger another rebalance. This is last-write-wins between trusted users (ADR 0010), as for any two clients that move into the same gap at once.
- Subtask families (ADR 0067) need one caveat. A card has its own stored column and key, and the board nests a child only under a parent in the same column, so within a column the order is the whole story. But `buildSubtaskHierarchy` (`packages/shared/src/subtasks.ts`) orders a parent's children by raw key across columns, and the card detail list, the MCP `subtasks` cursor (`board-do.ts`) and the family completion order (`family-completion.ts`) all read that order. Rewriting one column can therefore reorder a parent's children that live in different columns. That cross-column order was already arbitrary, since keys from different columns were never meant to be compared, so nothing is lost; the sort code is unchanged. A `subtasks` cursor taken before a rewrite can repeat or skip a child of that column, and a `card.finish` composed before one is refused by its placement guard, so the user retries.

## Consequences
- A rewrite writes one row per card in the column, and clients get one frame. It happens about once per 230 same-gap drops, never on ordinary moves.
- A frame lists every active card of the column (or every column), up to the wire's 10,000 entries. A longer list fails the client's parse, which closes the socket and reconnects with a fresh snapshot.
- Keys left over from before this change, 41 to 64 characters long in a column nobody writes a long key into, stay as they are. A gap already out of room refuses the drop at the schema, before the board sees it.
- Rejected: broadcasting a snapshot (see above), a client-side rewrite (the client cannot write many rows in one accepted frame without a new message), and a lower wire bound (still refuses, only sooner).
