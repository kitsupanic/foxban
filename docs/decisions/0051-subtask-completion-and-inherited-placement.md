# 0051 — Subtask completion and inherited placement

## Status
Superseded by 0067 — 2026-11-16 (accepted 2026-09-13)

## Context
Subtasks have been full cards linked by a `subtask` relation since ADR 0019, but the board rendered the child as a second root card in its own stored column with no completion of its own. We chose a parent-contained family (a "Subtasks" disclosure with connected child rows) and an **independent completion flag**, because a subtask shares its parent's column and therefore cannot have a status of its own. Two facts had to be settled: where completion lives, and where a child is placed while its parent moves.

## Decision
`Card.subtaskDone` is a required boolean column (DO schema v21, `subtask_done INTEGER NOT NULL DEFAULT 0`), independent of the parent's completion and of the child's own checklist; existing rows migrate incomplete because no historical source exists. Placement is derived, never stored eagerly: `buildSubtaskHierarchy` in `@foxban/shared` resolves active cards plus stored relations once per state change into parent/children/root/effective-column maps, and both BoardDO and the web reducer read it, so a child appears in its topmost active ancestor's column while its own `columnId` stays a fallback. A parent move therefore remains one `card.move` and one card row, and a direct move against a linked child is refused (`Subtasks share their parent task's status.`). New mutations `subtask.create` (child + relation + optional checklist conversion in one transaction) and `subtask.complete` (the child's own flag only) replace the three-send conversion; `REALTIME_PROTOCOL_VERSION` advanced to `"3"` because a version-2 bundle would read a fallback column as real and drop the new frames as unparseable. When a parent edge stops applying — unlink, parent archive, effective-column delete — the child's inherited column is materialized into its stored one before the edge goes, so the family keeps the column it was shown in; restoring a linked child returns it to its active parent's column regardless of the submitted destination. Legacy malformed forests are guarded rather than repaired: self/missing-endpoint edges, duplicate pairs, a child with two distinct parents and stored cycles are ignored by the resolver, and new subtask links are refused with `Invalid subtask hierarchy.`

Amendment — 2026-09-14: a linked child has the distinct immutable task type `subtask` (schema v22). Existing linked targets are promoted during migration; direct creation and relation linking write it immediately. `card.retype` refuses a subtask, and both subtask creation paths refuse a subtask parent. The UI therefore shows a read-only **Subtask** type and no **Add subtask** control on a child. Families are intentionally one level deep. `REALTIME_PROTOCOL_VERSION` advances to `"4"` because older clients expose both now-invalid controls and cannot interpret the new entity type.

Amendment — 2026-09-14: deleting a parent archives its complete active subtask family atomically. Every row receives the same archive timestamp and effective column; transfer locks are checked across the full affected set. Restore stays explicit per archived card. `REALTIME_PROTOCOL_VERSION` advances to `"5"` because older clients optimistically remove only the named parent.

## Consequences
The board, the card detail and close-focus all read one derived answer, so no surface can disagree and no row is renumbered. Materialization is confined to link and lifecycle changes, keeping moves cheap. A child is no longer a draggable board row and its details show a read-only inherited status instead of `StatusPicker`. Completion is per child and never cascades in either direction, so 3/3 children do not complete a parent. Older cards read `subtaskDone: false`. Rejected alternatives: storing the effective column on every child move (N writes and a second source of truth); replacing subtasks with checklist items (loses identifiers, attachments, comments and assignees); a per-child status picker (contradicts the shared column); and inferring initial completion from column names or checklist percentages (fabricates history).

Subtasks cannot recursively own subtasks, eliminating unbounded family nesting and the inconsistent generic Task picker on child details.
