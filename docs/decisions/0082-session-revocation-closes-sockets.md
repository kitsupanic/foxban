# 0082 — Revoking a session closes its open sockets

## Status
Accepted — 2026-11-19; amends 0026 and 0011.

## Context
A board or presence socket is checked once, at upgrade (0011). 0026 let a password change, and 0011 let a sign-out, leave an already-open socket alive, on the premise that removing a member behaved the same. It no longer does: member removal closes the board's sockets through the access-change fence (code 4010). A holder of a stolen session cookie with a socket already open kept reading and writing the board after the owner signed out or changed the password. Nothing on the socket said which session it came from, so nothing could close it.

## Decision
- At upgrade the Worker sets `x-foxban-session-hash`, the SHA-256 (hex) of the session id, on the request it forwards to the BoardDO or PresenceDO, and the object stores it in the socket's attachment (`sessionHash`). The raw id is a bearer secret and never leaves the Worker: on both paths the forwarded request is built by `upgradeHeaders`, which drops the browser's `Cookie` and `Authorization` as well as every `x-foxban-*` header it sent, before the Worker sets its own. Nothing in either object reads a cookie.
- `POST /internal/sessions/revoke` is a route of every BoardDO (gate `fence`: it needs only a board id, so it runs on a frozen or deleted board too) and of the PresenceDO, reachable only through the DO binding. Its body is `{ userId, sessionHashes }` or `{ userId, exceptSessionHash }`, exactly one, strict. It closes, with `ws.close(4011, ...)` (`SESSION_REVOKED_CLOSE`, distinct from the 4010 of an access change), every socket of that user whose hash is named, or whose hash is not the excepted one. A socket with no hash (accepted before this deploy) is named by any revocation for its user: it closes, and its owner reconnects with a hash.
- `revokeRealtimeSessions(env, ctx, userId, revocation)` in `auth.ts` runs after the session row is gone, in `ctx.waitUntil`, so the response is not delayed. It asks the PresenceDO at once, without waiting for D1, and meanwhile finds the boards the user can open with `boardOpenSql` (every board, for an instance Admin). The user and board reads are each tried twice; when both tries fail, a warning says the board fan-out was skipped for that user. It then asks each board's object in batches of 25 concurrent calls (the presence call finishes before the first batch), at most 500 calls in all, retries included. Every first call goes out before any retry. A call that gets no 2xx answer is retried once. The whole fan-out carries a deadline of 25 s from its start: `waitUntil` work is cut off about 30 s after the response (a platform assumption, not measured), so once the deadline passes it stops issuing calls and logs the boards not yet asked, and the ones that failed. What still has no answer, and every board past the cap or the deadline, is logged by id (the count, and the first 100 ids), never thrown. The cap is an assumption, not a measured limit: a Worker invocation may make at least 1000 subrequests on the paid plan (a platform fact that can change), the two D1 reads count against the same budget, and 500 leaves room for both. A Worker on a plan with a lower limit needs a lower `REVOKE_CALL_CAP`. The ids are logged so an operator can see which boards kept a socket; the same query lists them again.
- The upgrade race is closed by a second look, after the object accepts. In both upgrade routes, when the object answers 101, the Worker schedules in `ctx.waitUntil` (`recheckSessionAfterUpgrade`) a read of the session row by id and expiry. If the row is gone, it sends the same revocation, `{ userId, sessionHashes: [hash] }`, to that same object (`revokeIfSessionEnded`), with one retry, and logs a failure. The ordering argument: the session row is deleted before the fan-out starts, and the re-read starts after the object accepted the socket. Take the sweep's visit to that object. If the socket was accepted before it, the sweep sees the socket and its hash, and closes it. If it was accepted after, then the delete, which came before the sweep, came before the accept and so before the re-read, and the re-read sees no row and closes it. Either way a socket for an ended session is closed. The object accepts and writes the attachment in one step with no `await` between, so a sweep never sees a socket without its hash. A re-read that itself fails (D1 error) is logged and leaves the socket open: closing on a D1 hiccup would sign out people who did nothing, and the next sign-out, password change or reconnect covers it. A session that expires in the few milliseconds between the check and the re-read is closed the same way, which is harmless.
- Sign-out (`endSession`) revokes the hash of its own session, and only when its `DELETE ... RETURNING` removed a row. A password change revokes every session but the current one (`exceptSessionHash`), the same set it deletes from D1.
- The web client does not reconnect after 4011, on either socket. It leaves as a sign-out does: a full load of `/login`. The app has no global 401 handler (the `me` query is read once), so without this the person would see "Could not connect." on a board they can no longer open. The board socket first goes terminal (`signedOut` in `useBoardSocket`), then redirects: the browser's leave prompt over an unsent card draft can cancel the navigation, and the board must not stay on "reconnecting…". It then shows "You were signed out." with a Sign in link (the whole page when no snapshot had loaded; the draft stays visible when one had). The presence socket has no visible state of its own and only redirects.

## Consequences
A stolen cookie stops working on open sockets when the owner signs out or changes the password, as it already did for new requests and upgrades. The check stays at upgrade and at revocation: the BoardDO still reads nothing from D1 per message (0011's rejected alternative stays rejected).

Best effort, with two bounds. A board that gives no answer in 5 seconds, twice, keeps that session's sockets until they next reconnect, and the failure is logged by board id. A revocation for a user who can open more than about 500 boards (an instance Admin on a very large instance) leaves the boards past the cap, and logs them; so does one that outruns the 25 s deadline. If both reads of the user or board list fail, only the PresenceDO is asked and no board is (logged). A session that only expires (30 days) closes nothing. Each sign-out or password change wakes every board the user can open once, in the background.

The upgrade race is closed, not accepted. An upgrade that passed `requireAuth` just before the session row was deleted can reach `acceptWebSocket` after the sweep visited that object. That is not a rare accident: a holder of the stolen cookie can keep upgrades in flight on purpose, so that one is always past `requireAuth` when the owner signs out. The re-read after the accept (above) closes it. It adds one D1 read per accepted upgrade, in the background, not per message.

Assumptions the argument stands on: a D1 read that starts after a write has committed sees it (no read replica is used, and no stale session bookmark is passed); a Durable Object's answer to a fan-out call means it has swept every socket it had accepted by then; and `waitUntil` work that starts as the 101 is returned runs to completion.

Rejected: a per-message session check (a D1 read per mutation); handing the DO the raw session id (a bearer secret in the DO's storage); a socket registry in D1 (a second source of truth that drifts from the objects that actually hold the sockets).
