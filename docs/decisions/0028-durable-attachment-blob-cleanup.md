# 0028 — Durable attachment blob cleanup

## Status
Accepted — 2026-09-04; column-delete timing narrowed by 0034; amended by 0048 and schema v19

## Context
ADR 0027 kept deleted and failed-upload blobs in R2 so BoardDO mutations stayed synchronous, but that makes storage grow forever and leaves a retained raw URL readable after the UI says the attachment is gone.

## Decision
- BoardDO schema v9 adds an internal object key on attachment rows plus a durable cleanup queue. The Worker registers a one-hour provisional lease in that board's DO before writing R2; `attachment.create` claims it atomically.
- Attachment-row delete triggers enqueue the object in the same SQLite mutation, so individual, card and column deletions share one lifecycle. The DO starts immediate R2 deletion and uses an alarm-backed queue that reschedules after failures until deletion succeeds; successful deletion retains a permanent tombstone (schema v19 `deleted_at`, `reason = 'deleted'`, `delete_after = 0`, retaining `claim_token`) rather than deleting the cleanup row, permanently fencing the key against re-use.
- A daily Worker sweep lists valid R2 keys by board (both ordinary `boardId/attachmentId` and 3-part transfer-scoped `boardId/transferId/attachmentId` keys via `parseAttachmentObjectKey`). Each BoardDO protects attached objects and unexpired provisional uploads, then queues unowned keys without overwriting active claims; if an unowned key matches an existing tombstone (`deleted_at IS NOT NULL`), the DO transitions it from the idle tombstone state to an explicit redelete state (`delete_after = now`) to recollect late-arriving authorized bytes while continuously maintaining the publication fence. Successful redelete returns the tombstone to its idle state (`delete_after = 0`, alarm null), while failed redelete retains the claim fence and reschedules with bounded retry (`delete_after = retryAt`). Idle tombstones (`delete_after = 0`) are excluded from alarm scheduling and due work, preventing alarm loops.

## Consequences
Deletion is metadata-first and blob-eventual: peers lose the row immediately, while R2 removal follows through the durable queue. Upon successful R2 deletion, a permanent tombstone row is retained in `attachment_cleanup` with `deleted_at` stamped and `delete_after = 0` (idle tombstone state), ensuring the key is permanently retired and preventing re-staging or re-publication of the same key. Idle tombstones are excluded from alarm scheduling and due work. When reconciliation detects late authorized R2 bytes for a tombstoned key, it enqueues explicit redelete work (`delete_after = now`), draining the bytes while continuously maintaining the publication fence (`deleted_at IS NOT NULL`, `claim_token` non-null). Failure during redelete retains the fence and reschedules a bounded retry (`delete_after = retryAt`). Overlapping collectors converge idempotently without removing the fence. Fresh uploads and transfers must always use fresh UUID-backed keys. Raw URLs and Markdown embeds stop working once their attachment is deleted. Rejected: client-only DELETE calls, best-effort `waitUntil` without durable state, D1 attachment metadata, row deletion upon cleanup completion, and retaining orphaned blobs.
