# 0048 — Durable transfer fencing and operation history

## Status
Accepted — 2026-09-10 (supersedes in part ADR 0038; amended by schema v19 permanent tombstones)

## Context
ADR 0038 keyed destination transfer receipts by `(source_board_id, card_id)` and relied on a 5-minute lock TTL to prevent permanent editing lockouts. Under concurrent editing and failure recovery, this introduced severe data loss and obstruction failure modes: expired source locks permitted new edits that a delayed receipt retry subsequently deleted, historical receipts permanently prevented transferring a card back to a previously visited board, un-fenced worker compensation and direct foreground R2 deletion raced destination imports to delete copied R2 objects across generations, un-renewed publication leases permitted background sweeps to collect in-flight blobs, and concurrent attachment cleanup lacked claim tokens, risking race conditions between staging leases and background deletion.

## Decision
1. **Durable Operation Identity & Generation Tracking**: In BoardDO schema v18/v19, `card_transfer_operations(transfer_id PK, card_id, destination_board_id, generation, state, created_at, updated_at)` and `card_transfer_locks.generation` track transfer operation history across generations. Reusing terminated (`finalized` or `aborted`) `transferId`s is rejected with HTTP 409 Conflict.
2. **Non-Expiring Source Write Fences**: Source write locks (`isCardLocked`) do not expire via TTL. They remain engaged until a verified terminal transition (`finalized` or `aborted`). The `expires_at` timestamp serves strictly as an alarm recovery scheduling hint, never as an automatic write unlock.
3. **Exact Commit-or-Abort Destination Fencing & Safe Legacy Release**: `CARD_TRANSFER_ABORT_PATH` validates receipt identity. If uncommitted, it atomically inserts an abort tombstone receipt (`task_number = -1`). Destination import rejects aborted operations with HTTP 409 Conflict. In lock release (`CARD_TRANSFER_RELEASE_PATH`), destination identity is required; legacy release requests lacking destination board identity are rejected with HTTP 409 Conflict (`destination board identity unknown; lock retained`) and retain the source write fence.
4. **Operation-Keyed Receipts**: `card_transfer_receipts` is keyed by `transfer_id PRIMARY KEY` in schema v18/v19, decoupling historical receipts from card identity and allowing independent transfers of the same card across the same boards repeatedly.
5. **Transfer-Scoped Key Generation & Elimination of Foreground Compensation Deletion**: Transferred attachment blobs are copied to transfer-scoped destination keys `${destinationBoardId}/${transferId}/${attachmentId}` via `attachmentTransferObjectKey(destinationBoardId, transferId, attachmentId)` and registered with staging leases in `attachment_cleanup`. Transfer U import consumes only U's staging row, while aborted transfer T's staging rows remain collectible in `attachment_cleanup` until expired. Worker compensation performs **no foreground R2 deletion**; it establishes an atomic destination abort tombstone (`task_number = -1`) and releases the source lock, delegating uncommitted transfer-scoped blob collection entirely to the destination BoardDO TTL durable collector / alarm sweep, where successful deletion records permanent tombstones. This eliminates cross-generation deletion races where an aborted transfer could delete blobs belonging to a subsequent transfer.
6. **Pre-Write Import Validation with Rollback Exceptions**: In `CARD_TRANSFER_IMPORT_PATH`, the destination BoardDO validates receipts, duplicate card IDs, column existence, and active staging leases in `attachment_cleanup` (`delete_after > now AND claim_token IS NULL AND deleted_at IS NULL`) for all bundle attachments **before** executing any database writes or allocating destination task numbers. Any expired, claimed, or tombstoned lease or validation conflict immediately throws `ImportConflictError(409/400)`, triggering an atomic `transactionSync` rollback with zero partial aggregates or incremented counters committed.
7. **Exact-Key Ordinary Publication Validation**: Ordinary `attachment.create` synchronously validates that an exact matching cleanup lease by `object_key` (`${boardId}/${attachmentId}`) exists in `attachment_cleanup`, is in `'staged'` state, is unexpired (`delete_after > now`), and is unclaimed and not tombstoned (`claim_token IS NULL AND deleted_at IS NULL`) before inserting metadata into `attachments`. Any missing, expired, claimed, or tombstoned lease rejects the transaction with an error before any write, rolling back metadata insertion. The legacy `attachments_claim_staged_object` trigger was dropped in schema v18.
8. **Non-Overwriting Cleanup Claims, Restart-Safe Deletion Retry, Permanent Deletion Tombstones & Idle versus Redelete States**: BoardDO schema v18 added `claim_token TEXT` and `claimed_at INTEGER`, and schema v19 adds `deleted_at INTEGER` and index `attachment_cleanup_deleted_at` to `attachment_cleanup`. `drainAttachmentCleanup` atomically claims due rows (`UPDATE attachment_cleanup SET claim_token = ?, claimed_at = ? WHERE object_key = ? AND delete_after <= ? AND claim_token IS NULL AND deleted_at IS NULL`) before calling R2 batch delete. All queue writes, staging updates, and triggers (`attachments_queue_object_delete`) use conditional non-overwriting clauses (`WHERE attachment_cleanup.claim_token IS NULL AND attachment_cleanup.deleted_at IS NULL`) so active claims and permanent tombstones are never overwritten or reset. For previously claimed rows (such as following an interrupted sweep, DO restart, or tombstone redelete), the collector retains the exact existing `claim_token` and retries the idempotent R2 deletion. On R2 delete failure, the row is rescheduled with a bounded retry delay (`delete_after = retryAt`) while retaining `claim_token` non-null and maintaining the claim fence against conflicting staging/publication until successful R2 deletion. On successful R2 deletion, the row is NOT deleted; instead, a permanent terminal tombstone is recorded via `UPDATE attachment_cleanup SET deleted_at = COALESCE(deleted_at, ?), reason = 'deleted', delete_after = 0 WHERE object_key = ?`. Overlapping collectors converge idempotently on the tombstone without removing the fence. Terminal tombstones distinguish an **idle tombstone state** (`deleted_at IS NOT NULL`, `reason = 'deleted'`, retained `claim_token`, `delete_after = 0`)—which is excluded from alarm queries and due work (`WHERE deleted_at IS NULL OR (deleted_at IS NOT NULL AND delete_after > 0)`), preventing alarm loops—from an **explicit redelete state** (`delete_after = now` or bounded `retryAt > 0`). When global reconciliation observes late authorized R2 bytes matching an exact tombstoned key, the DO explicitly schedules redelete work (`delete_after = now`) and triggers alarm drain while continuously maintaining the publication and staging fence (`deleted_at IS NOT NULL`, `claim_token` non-null). Successful re-deletion returns the row to the idle tombstone state (`delete_after = 0`, alarm null), while deletion failure retains the claim fence and reschedules with bounded retry (`delete_after = retryAt`). All publication and staging remains rejected with HTTP 409 Conflict across both states. Keys are permanently non-reusable. All fresh uploads and transfers are required to generate fresh non-reusable keys (with UUID attachment IDs and safe 1–64-character Identifier transfer IDs).
9. **Full-Key Reconciliation & Tombstone Recollection**: Global and scheduled reconciliation (`reconcileAttachmentObjects` via `RECONCILE_ATTACHMENTS_PATH`) preserves full transfer-scoped keys (`parseAttachmentObjectKey` parses both 2-part ordinary `${boardId}/${attachmentId}` and 3-part transfer `${boardId}/${transferId}/${attachmentId}` keys without truncation, validating `transferId` against the API's safe `Identifier` grammar `/^[0-9A-Za-z_-]{1,64}$/` rather than assuming UUID transfer IDs, ensuring all keys accepted under the public contract can be recollected while preserving UUID validation for `attachmentId` and board grammar for `boardId`). The DO evaluates ownership, active unexpired staging protection, and existing tombstones against the full `objectKey`. Unowned, non-staged keys with existing tombstones are scheduled for explicit redelete (`delete_after = now`) and immediate alarm drain to recollect late authorized R2 bytes while continuously preserving the tombstone publication fence. Unowned keys without tombstones are queued as new orphans without overwriting active claims or tombstones; idle tombstones not seen in R2 remain excluded from alarm scheduling.
10. **Atomic Live-Avatar-Lease CAS Consumption & Invalidation**: Uploading a custom avatar registers a provisional lease in D1 `avatar_leases` (migration 0009). `/me/avatar` renews the lease after R2 upload and executes an atomic multi-statement D1 batch: a CAS update on `users` requiring an active lease (`UPDATE users SET avatar_version = ? WHERE id = ? AND ... AND EXISTS (SELECT 1 FROM avatar_leases WHERE user_id = ? AND version = ? AND expires_at > ?)`), lease deletion (`DELETE FROM avatar_leases WHERE user_id = ? AND version = ?`), and verification via `json('error: cas conflict')`. Expired leases abort the batch with HTTP 409 without mutating `avatar_version`. The background orphan sweeper atomically deletes expired leases before initiating R2 deletion, preventing delayed commits of collected blobs.
11. **Request-Triggered Legacy Recovery Wake-Up**: If a BoardDO boots or processes a request without `meta.board_id`, establishing its identity via incoming HTTP headers automatically inspects expired `card_transfer_locks` and schedules deterministic alarm recovery via `scheduleAlarmAt(Date.now())` and `waitUntil(recoverExpiredTransferLocks)`.
12. **AST-Based Markdown URL Rewriting**: `rewriteAttachmentUrls` remaps attachment URLs using exact parser token offsets from `mdast-util-from-markdown`, handling inline code backticks, brackets, entity encodings, and angle brackets natively.
13. **Stable Terminal-Transfer Error Code**: Every rejection that makes a `transferId` permanently unusable carries the machine-readable discriminator `code: "transfer_terminal"` (`TRANSFER_TERMINAL_CODE` in `packages/shared/src/protocol.ts`, re-exported from `@foxban/shared`) beside its HTTP status. This covers reused or terminated operation ids, card and destination identity mismatches, generation mismatches, abort tombstones (`task_number = -1`), transfer lock mismatches, and `destination board identity unknown; lock retained`. Both BoardDO responses (`apps/api/src/board-do.ts`, including `ImportConflictError`) and the Worker saga routes (`apps/api/src/index.ts`) emit it, and the Worker preserves the code when relaying a DO 409 or 410 rather than collapsing it to opaque prose. `isTerminalTransferConflict` in `TransferCardDialog` tests the code first, then HTTP 410 / `aborted: true`. These are the only terminal signals: an uncoded 409 is non-terminal no matter how terminal its prose sounds, so the operation id is preserved for idempotent retry and no new-operation notice is shown. Human error text is display-only.

## Consequences
- Cross-board transfers cannot silently discard post-expiry source edits, collide with historical receipts, or delete blobs belonging to subsequent transfers.
- Foreground compensation never deletes R2 keys directly; uncommitted transfer-scoped blobs are collected safely by the destination TTL durable collector, with successful deletion leaving permanent tombstones that prevent key reuse.
- Transfer U consumes only U's staging row, while aborted transfer T's staging row remains collectible in `attachment_cleanup` until expiry, after which R2 deletion records a permanent tombstone.
- Ordinary attachment creation validates exact unexpired unclaimed non-tombstoned staging leases, rolling back before metadata insert if missing, expired, claimed, or tombstoned.
- Cleanup claims are non-overwriting, failed or interrupted deletions retry under the same claim token while maintaining the claim fence, and successful R2 deletions persist permanent tombstones (schema v19 `deleted_at`) with `delete_after = 0` (idle tombstone state) rather than removing rows. Idle tombstones are excluded from alarm scheduling and due work, preventing alarm loops. When reconciliation encounters late authorized R2 bytes for a tombstoned key, it enqueues explicit redelete (`delete_after = now`) and drains the bytes, returning the tombstone to idle upon success or scheduling bounded retry on failure while continuously maintaining the publication fence. Staging or publishing any tombstoned key remains permanently rejected with HTTP 409 Conflict.
- Full-key reconciliation preserves transfer-scoped keys across all safe transfer identifiers accepted by the API contract, active claims, and tombstones.
- Import failures roll back transactionally before committing metadata or bumping task numbers.
- Avatar updates consume live leases atomically in D1, preventing publication of orphaned or expired blobs.
- Unreachable destinations and destination-less release calls preserve source write fences until destination state is verified.
- Terminal transfer rejections are machine-classifiable: the client rotates to a fresh operation id only on `code: "transfer_terminal"`, HTTP 410, or an explicit `aborted` flag, never on response prose. Rewording a server error can no longer turn a terminal conflict into an endless retry against a dead operation id, and a terminal-sounding message on an uncoded 409 cannot rotate an operation that is still live. Server error strings stay free to change.
- Supersedes ADR 0038's composite-keyed receipts, deterministic legacy transfer keys, direct foreground compensation deletion, and TTL-based unlocking semantics.
