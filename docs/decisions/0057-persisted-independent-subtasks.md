# 0057 — Persisted independent subtask workflow

## Status
Accepted — 2026-10-01. Supersedes ADR 0051 only on explicitly configured boards. The isolated ADR 0056 trial remains available.

## Decision
A subtask is a task with one parent relation and its own stored column. Moving a parent or child updates one card row and never moves the rest of the family. Same-column children nest under the active parent; children elsewhere appear once as ordinary draggable card faces with a parent navigation link. Grouping is presentation, not persisted placement. Direct active child progress spans all columns, independent of filtering and parent status. Checklists remain boolean inline steps.

BoardDO SQLite schema v25 adds explicit `starting` and `completed` metadata to columns. Exactly one distinct starting and completed column is selected by an owner/admin through `workflow.configure`; names, order and labels have no semantic meaning. New subtasks start in the starting column; converting a completed checklist item creates the child in the completed column. Completion is derived from the child's own column. `subtaskDone` stays on the wire for older reader contracts and as legacy migration/archive evidence, but cannot be changed independently on an activated board. MCP `complete_subtask` moves a linked child to the completed/starting column in independent mode, while legacy boards retain the boolean behavior. Tool descriptions explicitly state both modes. MCP move anchors include independent children.

## Safe activation and compatibility
The additive schema change alone does not convert placement. Existing and new boards retain legacy inherited semantics until configured. Activation submits one reviewed destination/order for every active subtask, including detached children. Completed children are proposed for completion; incomplete children retain their displayed column. Incomplete children under completed parents and detached children require explicit choices. Detached children are promoted to ordinary tasks, removing their retained incoming subtask links in the same transaction so restoring an archived parent cannot reattach them. Status labels remain ordinary labels and are not interpreted or silently rewritten.

The settings require a before-change JSON export and an explicit review acknowledgment. Changes to cards, relations or columns invalidate the export/review. Server transaction checks prior workflow mapping plus each child's stored column, old completion, parent and displayed column, then commits all placements and column roles atomically. Transfers fence configuration. Workflow reconfiguration previews completion/reopen counts and changes no card placement.

Realtime version 8 gates new handshakes and is persisted in hibernating socket attachments. Incompatible sockets are closed before mutations/content frames; a reconnect obtains the new client protocol. Deployment must publish API and web together. No Node runtime storage or card state in D1.

## Lifecycle
Archive is per task; links remain retained and inactive while an endpoint is archived. Children stay in their statuses when a parent is archived. Restore selects an explicit destination even with a retained parent. Archived completion is frozen as history, then recomputed from destination on restore. Unlink promotes the child to `task` without moving it; purging a retained parent promotes surviving children. Starting/completed columns require reassignment before deletion. Other column deletion archives only cards actually in that column. Crossboard transfer retains the existing requirement to remove all links first; imported standalone subtasks become ordinary tasks, and destination column semantics decide completion. Moving an entire family across boards is outside this change.

## Rollout / rollback
No live conversion is run by this change. Before a rollout, inspect the target board's snapshot and choose its starting and completed columns, review exceptional children and conflicting status labels, download the workflow export, and obtain a recoverable BoardDO SQLite backup/PITR point using the established operations procedure. The UI export is review evidence, not a complete database/R2 backup.

Deploy the verified API/web together only when requested. Confirm an unconfigured board retains the legacy workflow; activate a disposable dev board before any live board. Confirm snapshots, children in each status, progress, two-client updates, reconnects and old-client reload behavior.

Rollback must restore data before returning to inherited client behavior: freeze board writes, restore the pre-activation SQLite backup/PITR point (or execute a separately reviewed workflow-only restoration from exported ids, columns, positions, types, boolean evidence and relations), confirm original column flags/placement/completion and retained archives, then restore the prior API/web version and reconnect every client. Restoring an old binary alone would reinterpret independent columns as inherited placement and is not a safe rollback. Workflow settings deliberately provide no implicit reverse migration or unreviewed import button. Back up attachments separately when performing full database recovery; this migration changes no R2 objects or D1 card data.
